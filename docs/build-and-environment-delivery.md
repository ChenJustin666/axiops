# 构建、环境资源与跨环境发布

适用版本：2026-10-02 本地 AxiOps。以下主要针对 Kubernetes YAML 服务、Kubernetes 构建 Agent。

## 1. 创建项目后返回列表

点击“立即创建”后，会刷新项目列表并进入该项目。返回列表会重新读取项目，无需按浏览器刷新。创建时会清除旧的搜索、分类和分页条件，避免新项目被旧筛选条件挡住。

项目创建与项目初始化是两件事：创建后仍可按初始化向导完善服务、环境、构建配置和工作流。中途退出，已保存的内容保留；再次进入继续未完成的步骤。未保存的编辑内容仍需先保存。

## 2. Job 编号与构建编号

- 工作流 Job 的执行次数按该工作流独立编号：第一次 `#1`，随后 `#2`。不同环境的工作流各有自己的计数。
- 服务的镜像构建记录沿用每个服务独立的 `build_number`。同一服务从不同环境触发新构建，会继续这个服务的构建序号。
- 两者不是同一个计数：复用镜像发布会新增一次 Job 执行，但不会新增镜像构建记录。
- 全局数据库 ID 只用于详情链接、日志关联和排查，不能当作构建次数。旧记录已按所属 Job 回填显示编号，没有删除或重新执行。
- 例如原链接中的运行 ID `40` 保持不变，但在其所属的 sinozo 生产 Job 中，它是第一次执行，页面显示 `#1`。

## 3. 仓库没有 Dockerfile，如何构建

无需为了使用平台额外向仓库提交 Dockerfile，可以在构建配置中保存。平台仍需要真实的代码仓库、分支、编译方式和镜像仓库；它不会猜测任意项目的编译命令或产物路径。

### Java 单模块：先编译 JAR，再打镜像

以 `ad-gateway` 为例：

1. 进入项目 → 构建配置，点击服务的“编辑构建”。也可从服务配置打开“构建配置（共享）”。
2. 选择代码源、代码仓库、分支；选择镜像仓库和命名空间，产物镜像名沿用服务绑定，通常不需要重复填写。
3. 在“Dockerfile 来源”选择“平台模板 / 编辑”。
4. 可以直接从 Dockerfile 模板库选择已保存模板；Java 服务也可点击“使用 Java 17 JAR 示例”。此按钮会选择“JAR 镜像”模式并带入已有的 Maven / JDK 17 编译默认配置。
5. 检查编译镜像和编译命令是否与项目一致。默认 Maven 命令在仓库根目录运行，执行 `clean package`，包含测试；项目使用 Gradle 或其他 JDK 时更换对应配置。
6. 构建上下文填 `.`。把示例中的 `COPY target/*.jar` 改为实际的唯一 JAR 文件，避免一个目录有多个 JAR 时复制失败。例如：

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY target/ad-gateway-1.0.0.jar app.jar
ENV JAVA_OPTS=""
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]
```

7. 保存配置，再进入测试环境对应的工作流 → 执行工作流 → 重新构建并部署。
8. 检查编译日志、镜像推送和部署就绪检查。`COPY` 文件不存在时，要先确认编译产物、构建上下文及 `.dockerignore`，不要只修改文件名绕过报错。

此 Dockerfile 只负责把已经编译的 JAR 打入镜像，因此必须搭配“JAR 镜像”模式。若选择“Dockerfile / 多阶段”，应提供能够自行编译项目的完整多阶段 Dockerfile，或者确保所复制产物本来就在构建上下文中。

服务实际端口在服务 YAML/环境变量中配置；Dockerfile 的 `EXPOSE` 不能替代应用监听端口与 Service 的 `targetPort`。例如应用监听 9099，Deployment 与 Service 也应使用对应端口。

### Maven 多模块：保留父 POM 和依赖模块

例如仓库根目录包含父 `pom.xml`，以及 `card-scout-common`、`card-scout-gateway` 等模块：

1. 仍选择“JAR 镜像”，在仓库根目录编译。
2. 编译命令可填：

```sh
mvn -B -ntp -Dmaven.repo.local="${CACHE_DIR:-/workspace/.cache/maven}" -pl card-scout-gateway -am clean package
```

3. 构建上下文保留 `.`；平台 Dockerfile 中的 COPY 使用完整模块路径：

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY card-scout-gateway/target/card-scout-gateway-1.0.0.jar app.jar
ENV JAVA_OPTS=""
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]
```

4. JAR 名称以上述项目实际输出为准。父 POM、兄弟模块依赖仍可参与编译，不需要分别先部署依赖模块。

如果仓库已经有 Dockerfile，可继续用“代码仓库”来源：单模块选根 Dockerfile；多模块按仓库文件选择器选择对应文件和构建上下文。

平台 Dockerfile 会随构建配置进入执行快照；排队后再修改模板，不会改写已经提交的构建。当前此来源支持 Kubernetes 构建 Agent；主机/Jenkins 执行器暂不接收这份平台 Dockerfile，界面/后端会拒绝不兼容组合。

## 4. 同一服务在测试、生产使用不同 CPU/内存

入口：项目 → 服务配置 → 选中服务 → 顶部环境下拉框。

“共享模板”放 Deployment、Service 等基础 YAML；环境下拉框中分别维护测试、生产的覆盖。服务必须先“加入此环境”。

1. 切换到测试环境。
2. 展开“运行资源与配套配置：CPU / 内存、文件、密码、域名、存储”。
3. 在“CPU / 内存”页打开“覆盖当前环境运行资源”。只有一个工作负载、一个容器时可自动识别；多个时明确选择目标工作负载与容器。
4. 例如填写：

| 字段 | 测试示例 | 生产示例 |
|---|---|---|
| CPU request | `250m` | `1` |
| CPU limit | `1` | `2` |
| 内存 request | `512Mi` | `2Gi` |
| 内存 limit | `1Gi` | `4Gi` |

5. 点击“检查并预览”，展开“查看生成的部署 YAML”，核对目标环境、容器和 `resources`。
6. 点击“保存配置，待发布”。生产环境需先勾选核对确认；这一步只保存，不部署。
7. 切换到生产环境，按生产需要单独填写、预览并保存。测试值不会自动覆盖生产值。
8. 执行该目标环境的部署。只改资源限制时可选择已有成功镜像，不必重新构建。
9. 部署结束后到该环境的运行资源查看实际 Deployment/Pod 配置和就绪状态；配置保存成功不等于应用部署成功。

明确规则：

- `request` 是调度申请，`limit` 是上限。使用 `512Mi`、`1Gi`、`4Gi`；不要填 `1g` 或用裸数字 `1` 表示 1 GB。CPU 可以填 `500m` 或 `1`。
- 只覆盖填写的字段，留空继承共享 YAML。关闭覆盖后恢复共享 YAML，**不等于强行取消模板中的限制**。模板也没有设置时，平台不主动增加该限制；集群自己的 LimitRange/ResourceQuota 等策略仍可能影响准入和默认值。
- 保存会校验格式及合并后的 request ≤ limit。模板已有 request=2Gi 时，不能只把环境 limit 改成1Gi；需要一起调低 request。
- 保存后需重新部署才对新 Pod 生效。运行已排队时，后续修改不改变该次执行的配置快照。
- 这是服务运行资源，和“构建配置 → 高级构建设置”里的 CI 构建 Pod 资源是不同配置。
- “同步到其他环境”仍只同步明确勾选的模板版本、变量；本表单的资源、文件、凭据等配套配置不会被此按钮一并复制。不同环境的资源应分别设置。
- Helm 服务使用该 Chart 实际引用的 values 路径，例如 `resources.limits.memory`。只有 Chart 模板读取此值时才生效；当前通用 CPU/内存表单针对 Kubernetes YAML，不能把任意 Chart 当成固定结构。

## 5. 测试构建成功后，部署到其他环境

原则：**复用同一个已验证镜像，部署时使用目标环境自己的配置。** 环境名称不是必须重新构建的依据。

操作步骤：

1. 先确保目标环境已经创建并绑定正确集群和 Namespace；将服务加入目标环境，保存该环境的变量、资源、域名、配置文件和凭据引用。
2. 打开绑定目标环境的工作流。例如部署生产，打开生产工作流，不在测试工作流的执行框里临时改成生产。
3. 点击“执行工作流”，选择“使用已有成功镜像（不构建）”。支持该模式的生产环境默认选中此方式。
4. 选择本次要发布的服务，再从成功构建中明确选择一个版本。下拉框显示构建编号、分支、Commit 和时间，选中后显示镜像及 `sha256` 摘要；可通过“更早构建”逐页查找。
5. 核对右侧固定目标环境、集群和 Namespace，提交执行。没有合适镜像时会提示，不会偷偷改成重新构建。
6. 运行详情显示“使用已有镜像 · 源构建 #… · 本次未重新构建”，可在代码变更页查看源构建的记录。已有审批规则继续生效，不绕过生产校验。
7. 在部署节点日志查看资源提交、就绪检查和失败原因，再到目标环境核对运行资源。

此次执行只从源构建取得固定的镜像及摘要，不复制源环境的数据库地址、密码、域名、资源限制或 Namespace。镜像带 `test/qa` 标签不代表只能部署测试：所选摘要确定镜像内容，目标工作流确定部署位置。

| 情况 | 建议选择 |
|---|---|
| 修改业务代码，要生成新版本 | 重新构建并部署 |
| 修改 Dockerfile、编译命令、编译参数或要更新基础镜像 | 重新构建并部署 |
| 测试已验证同一版本，发布到预发布/生产 | 使用已有成功镜像 |
| 只修改环境域名、数据库地址、资源限制或挂载配置 | 使用已有成功镜像，并部署目标配置 |
| 目标环境依赖编译期参数，或要求不同 CPU 架构而原镜像不兼容 | 生成匹配产物后再部署；不能假定原镜像通用 |
| 没有成功构建，或旧记录没有镜像摘要 | 先成功构建一次 |

当前新增的复用入口支持可单服务执行的 Kubernetes YAML 工作流；包含独立测试节点、Helm/主机部署或复杂混合节点的工作流不会自动删除这些步骤，不提供此快捷模式。旧“发布草稿”入口也没有自动等同此模式，请从工作流的“执行工作流”使用。

目标集群仍需要能访问镜像仓库，并拥有拉取权限。复用不会自动把镜像复制到另一个仓库；出现 `ImagePullBackOff` 要检查目标环境的拉取凭据、镜像是否仍保留及集群网络。部署结果必须以就绪检查为准。
