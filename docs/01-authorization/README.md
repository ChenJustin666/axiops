# 权限模块

## 产品定位

权限模块统一管理用户、直属部门、角色、菜单、动作权限和资源范围。角色定义“能做什么”，绑定定义“能对哪些项目、服务、构建、集群或环境做”。前端菜单用于改善体验，后端授权才是安全边界。

## 已确认需求

- 同时支持权限中台集成和 AxiOps 内建账号、部门、角色与授权。
- 用户和直属部门可以绑定资源范围角色；当前不隐式继承子部门。
- 支持 `platform/project/service/build/workflow/cluster/environment` 范围。
- 支持 `view/create/update/delete/run/cancel/deploy/approve/rollback/export` 动作。
- 默认拒绝，显式 `deny` 优先，临时授权到期自动失效。
- 开发和测试角色默认是资源范围角色，不得通过平台角色获得全局权限。
- 运维和平台管理员分离：运维负责生产资源，平台管理员负责用户、角色、菜单和授权。
- 禁用或删除用户即使 JWT 尚未过期，也不能继续获取有效策略。
- 所有认证后的写请求写入审计日志，请求体不入库，避免泄漏密码、Token、凭据和 kubeconfig。

## 权限模型

```text
allow = action_permission
     && resource_scope_match
     && environment_policy_pass
     && no_explicit_deny
```

绑定职责固定如下：

| 数据模型 | 用途 |
|---|---|
| `user_role` | 只绑定 `binding_scope=platform` 的平台角色 |
| `project_member` | 用户在指定项目中的 `scoped` 角色 |
| `role_binding` | 用户或直属部门在服务、构建、集群、项目或环境范围内的 `scoped` 角色 |

内置 `operator` 是平台级运维角色；需要限制到指定集群或项目时，应创建 `scoped` 运维角色后使用 `role_binding`，不能把平台角色直接降格绑定。

详细数据结构、策略和接口见[详细设计](DESIGN.md)，旧/新认证过渡见[身份收敛方案](IDENTITY_MIGRATION.md)。

## 实施计划

1. 完成统一授权内核和 CI/CD 资源级鉴权。
2. 完成用户、角色、项目、成员、凭据和集群 API 鉴权。
3. 完成角色绑定、当前菜单、权限预览和审计 API 闭环。
4. 完成新 `/api/v1` 用户、部门、角色、菜单和资源范围授权页面。
5. 发布、Helm、监控、日志和 AI 查询复用同一授权内核。

## 当前结论

- 后端权限闭环已完成并通过相关 Go 测试。
- 权限中心前端已接入新接口，覆盖用户、部门、角色权限矩阵、显式拒绝、菜单树和资源范围授权。
- 项目、服务、环境、构建、工作流和集群均可作为授权目标；工作流已按独立 ID 做后端过滤和二次鉴权。
- 代码门禁已通过；数据库迁移和真实登录态浏览器 E2E 尚未执行，因此整个权限模块暂不标记为生产验收完成。
- 部门只匹配用户直属部门；部门树递归继承作为明确的后续能力，不做隐式行为。
- 凭据和 kubeconfig 的静态加密属于工程安全任务，不能因接口已鉴权就宣称敏感数据安全完成。

具体完成项和测试命令见[完成进度](PROGRESS.md)。

## 验收标准

- 项目 A 用户无法读取项目 B 的服务、构建、日志、数量或详情。
- 只读用户不能触发、取消、修改、部署或回滚。
- 生产部署只允许拥有对应环境、集群和发布动作权限的角色执行。
- 平台角色不能通过资源绑定下放，资源角色不能进入平台角色绑定。
- 平台管理员不能分配、修改或移除超级管理员及其等价的 `*`、`system_role` 权限。
- 禁用用户立即失去有效策略；权限变更不依赖 JWT 内的旧权限快照。
- 写操作有可检索审计记录，且不保存敏感请求体。
