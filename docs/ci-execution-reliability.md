# 构建并发、恢复与清理

这套规则由公共构建 worker 管理。当前实际执行器为 Kubernetes Job；宿主机构建适配接口已要求相同的恢复和清理协议，但尚未接入实际宿主机构建 agent。宿主机部署 agent 不等于宿主机构建执行器。

## 资源池与并发

- 管理入口：系统管理 → 构建资源。平台和项目并发上限共同生效，`dispatching / running / cancelling` 都占用额度。数据库锁串行化派发决策，多个 worker 不会各自重复计算额度。任务排队存于 MySQL。
- 同一节点允许多个构建。可配置节点标签、精确污点容忍、每节点并发上限、CPU/内存、临时磁盘上限。每节点上限用固定槽位标签和 required Pod anti-affinity 实现，作用范围为该 CI Namespace；有空余资源时也可能因同槽位被占用而短暂等待。终态保存后移除 Pod 槽位标签，保留排查 Pod 不继续占用槽位。
- 每节点上限为 0 时只按 Kubernetes 资源调度。填写 CPU/内存时，git-clone、JAR 编译、builder 都使用对应的 requests/limits；服务非空值覆盖平台。两处都空时平台不预留、不限额，仍受 Kubernetes LimitRange/Quota 约束。它不等于每个任务独占整个节点，也不保证不会耗尽节点。
- 单台 4 核 8 GB 的起步参考是并发 2 个，每个 1 CPU / 2Gi，给系统及其他组件留余量。最终要按节点 **allocatable**、Java 堆及实际构建峰值调整；大项目可能只能同时跑一个。此参考不会自动覆盖已有资源配置。
- 临时磁盘上限同时作用于源码 emptyDir、临时缓存和容器临时存储。PVC 不受 emptyDir 上限约束，应单独设容量。磁盘容量和 inode 都需监控。
- 示例节点标签为 `axiops.io/ci-pool=ci`。只有匹配标签的构建节点需满足 BuildKit 前置条件；业务部署节点不需要因此全部更改。现有 RootlessKit builder 仍使用 privileged/unconfined，必须按专用 CI 节点池的信任边界部署。平台不会自动修改 sysctl 或扩大权限；见 [RootlessKit 排查](ci-rootless-buildkit.md)。

## 任务生命周期

| 场景 | 行为 |
| --- | --- |
| API 重启 | 队列、配置快照和状态保留在数据库 |
| worker 在创建 Job 后、写回结果前退出 | 租约回收后先按 run ID/idempotency key 找回同一个 Job，再读取凭据；不会因凭据已轮换而重复构建 |
| 最后一次提交尝试中重启 | 不将进程退出计作执行失败，仍允许接管；已经写回 running 的提交命令会收尾为成功 |
| 创建请求超时、结果不确定 | 保留凭据和执行额度，指数退避查询原任务；不能仅凭超时断言 Job 没有创建 |
| 普通确定的提交错误 | 使用配置的重试次数，默认 3 次，退避最大 60 秒；失败原因可见 |
| Git 网络抖动 | 同一个仓库 fetch 最多 3 次，每次最多 120 秒，间隔 3/6 秒；认证、无效分支等确定错误不重复尝试 |
| 构建无输出、死锁或一直 Pending | Job 自身 activeDeadlineSeconds 负责总超时，包含调度、拉代码、编译和推送；即使 worker 离线也由集群终止 |
| 镜像拉取暂时失败 | Kubernetes 自身退避重试，受构建总超时约束，页面显示等待原因 |
| 编译错误、OOM、被驱逐、节点缺少用户命名空间 | 保存退出原因和日志；不自动扩大资源、修改内核或重跑任意业务脚本 |
| Job 被外部删除/历史 TTL 已删 | 明确记录执行对象丢失并结束平台任务，不再一直显示 running；已丢失的原始输出无法恢复 |
| 用户取消 | 等进行中的提交确认后，按固定身份找回 Job，先采集可读取日志，再前台删除；等 Job/容器停止后才释放执行额度 |
| 控制面持续不可达 | 保持“待确认/取消中”及诊断，持续查询原任务；不虚报取消成功。Job 的总超时仍独立生效 |

任意用户构建命令可能有外部副作用，所以平台不会自动重跑整个命令来掩盖失败。修复不可恢复的问题后，通过新构建重试。

## 源码、缓存、日志与产物

- 源码按每次构建隔离在 emptyDir，权威版本仍在 Git，通过构建保存的提交号追踪。临时源码不是长期制品；节点丢失、kubelet 清理或 Pod 删除后不保证工作目录可取回。
- 默认临时缓存随 Pod 生命周期清理。持久缓存按 `project-N/service-N` 隔离；同服务使用 PVC 时串行派发，避免 Maven/Gradle 等并发写同一目录。明确 emptydir 可并发，其他服务可并发。只有 YAML 引导配置、尚未保存平台设置时，对继承缓存保守串行。PVC 不会自动删除其他服务数据，需存储容量和保留策略。
- 新 Job 创建时不启用 TTL。平台先保存状态、日志和产物校验结果，再持久标记“待清理”；默认 0 秒时由后台幂等清理器主动前台删除 Job，并确认删除后收尾，不依赖 TTL 控制器。主动设置额外排查保留时才为 Job 设置 TTL、释放调度槽位并删除临时凭据。中途重启或清理 API 失败都会再次尝试。
- 成功、失败、超时采用相同 Job 保留配置，默认 **0 秒**：平台确认结果与日志保存后，主动请求前台删除 Job 和 Pod，无需再等 24 小时。级联回收由集群控制器异步完成，未确认删除时继续保留待清理标记并重试。页面中的构建记录和已保存日志独立保留；worker 离线或保存失败时，仍先恢复采集/保存，再清理。额外保留时间仅作为主动选择的排查选项，从平台确认保存起算。取消会停止并删除执行对象，已采集日志仍保留。
- 已停止的容器不持续消耗构建 CPU/内存；保留的 Pod 元数据、日志文件及节点缓存仍可能占用存储。平台长期停机时，没有确认的 Job 将保留，需对 CI Namespace 的已完成 Job 数量和节点磁盘设置运维告警。
- 当前日志采集是**有上限的快照**，不是无限完整流式日志：未配置对象存储时约 1 MiB，配置时约 8 MiB，按容器分配额度；超出会标记截断。kubelet 轮转前未采集的输出不保证找回。需要大规模完整日志时，应另接集群日志采集系统。
- 对象存储写失败会退回 MySQL 保存最多 1 MiB，并显示诊断，不阻塞最终结果；读取归档失败会显示数据库尾部，避免日志页面空白。临时最终日志读取失败最多补采 5 分钟，之后保留缺失提示与可用片段；产物校验网络失败也有 5 分钟确认窗口，无法确认则失败，不假报成功。
- 日志保留天数 0 表示兼容旧配置、不自动删除；可选择例如 30 天。该规则对历史终态日志也生效。先删除已关联的归档对象，再将数据库正文换成清理说明，保留构建结果与产物引用。归档连接失效时保留记录并重试；对象存储仍建议配置桶级生命周期，覆盖失败上传、旧版本等孤立对象。
- 镜像/制品保留由对应 Registry/制品仓库策略管理，Job 清理不删除发布所依赖的产物。

## 启用与维护

1. 应用迁移：`go run ./cmd/axiops-migrate -f configs/platform-api.yaml`。
2. 更新 CI/CD API 和 workflow-worker；新 worker 的 Git 重试和 Job 生命周期无需重新发布 builder 镜像。RootlessKit 启动前检查脚本仍需发布新版 builder 才能生效。
3. 在构建资源页选择 CI 集群、节点标签和并发策略。Kubernetes 凭据需有 CI Namespace 中的 Job create/get/delete/patch、Pod list/get/patch/log、Secret create/get/delete 权限。预先创建 Namespace 可避免授予 Namespace 创建权限。
4. 改集群、Namespace 或节点策略前，停用新任务派发并等待运行及待清理任务收尾。服务端拒绝在有遗留执行时迁移构建池。停用期间继续观察已有任务。
5. 保存执行器参数后重启 workflow-worker。旧 worker 会停止按过时参数派发新任务，同时继续观察/恢复已有任务；并发上限及停用开关通过数据库即时生效。不要直接迁移或删除尚未收尾的执行记录。

## 后续宿主机执行器的接口要求

`ECSAgentDispatcher` 除 Submit/Status/Cancel 外，现在必须实现 `RecoverBuild` 和 `FinalizeBuild`，复用公共队列、日志保存、校验、终态和清理流程。

- agent 使用持久执行台账保存 run ID、幂等键、进程/容器身份、开始时间和截止时间；不能仅依赖内存 PID，必须防止 PID 复用。
- 每个 agent 有总并发、资源和磁盘预算；Linux 使用 cgroup/容器限制，资源空值则共享但仍受并发上限约束。
- 按构建编号创建独立工作目录和凭据目录，依赖缓存需要隔离/锁；清理只作用于验证过的 agent 工作根目录内部。
- worker 断线时 agent 继续执行并独立强制总超时；取消需要停止整个进程组/容器并确认退出。
- 结果及日志在平台 Finalize 确认之前保留，agent 重启从台账恢复；不得无条件重跑带副作用的构建脚本。

这些是宿主机构建接入的验收条件，目前不能把已有部署 agent 当作已支持完整构建生命周期。
