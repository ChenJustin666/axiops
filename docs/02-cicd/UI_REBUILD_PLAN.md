# AxiOps CI/CD 前端重构计划

更新时间：2026-09-07

## 重构判断

这不是继续堆功能的局部优化，而是 CI/CD 工作台的前端重构。后端已有的项目、服务、Revision、环境、工作流、运行记录和权限接口继续保留；前端重新组织路由、组件边界和交互流程。旧弹窗暂时保留用于回归测试，重构完成后再移除入口。

## 目标页面

```text
项目工作台
├── 顶部：项目上下文、交付类型、环境筛选、服务搜索、发布批次
├── 左栏：服务目录、标签、状态、Revision 列表
├── 中栏：服务 × 环境矩阵、构建产物、部署状态
└── 右栏：当前服务详情、环境覆盖、Diff、发布操作
```

固定项目内导航：概览、服务与环境、工作流、运行记录、制品、变量与模板、设置。默认进入“服务与环境”，而不是把所有内容放入概览。

## 服务创建流程

新建服务使用页面级三步向导，不再用一个大表单承载所有配置：

1. 选择创建方式：手工输入、代码库同步、模板创建、克隆已有服务。
2. 识别服务：仓库、分支、目录、语言、Dockerfile、YAML/Helm、镜像地址，以表格预览并允许逐项取消导入。
3. 交付配置：构建模板、默认环境、组件、探活、发布策略和工作流模板。

无论服务数量是一项还是批量导入，完成后都进入同一套服务目录和 Revision 模型。

## 服务详情工作台

服务详情改成固定三栏页面：

- 左栏：服务元数据、组件目录、Revision 历史、同步状态。
- 中栏：YAML/Helm values/主机部署脚本编辑器、格式化、校验、Diff。
- 右栏：镜像、构建配置、健康检查、变量、环境覆盖和权限提示。
- 底部操作条：保存为新 Revision、从代码库同步、预览 Diff、发布。

修改副本数、镜像、变量等运行参数只生成环境覆盖；修改资源结构必须生成新的服务 Revision，避免直接覆盖基线。

## 发布流程

发布入口从服务环境矩阵发起：

```text
选择服务 -> 选择 Revision/镜像 digest -> 选择一个或多个环境
-> 展开集群和 Namespace -> 查看 YAML/Helm Diff
-> 选择滚动/金丝雀/蓝绿 -> 预览 build/test/deploy Job
-> 生产审批 -> 执行发布批次
```

构建 Job 按服务和 Commit 生成一次，产出不可变镜像 digest；测试 Job 按测试套件或服务生成；部署 Job 按发布批次的环境、集群和 Namespace 生成。这样同一个镜像可以在测试、预发布和生产复用，不会因为环境数量重复构建。

## 实施顺序

### P0：页面骨架

- 修复 CI/CD 页面中文编码，统一 UTF-8 文案和状态字典。
- 新增项目工作台布局和固定导航。
- 将服务环境矩阵设为默认页面。
- 保留权限判断、服务和环境 API，不新增 SQL。

### P1：服务工作台

- 将 `ServiceDetailDrawer` 改为页面级三栏工作台。
- 接入 Monaco/YAML 编辑、Revision 保存、Diff 和环境覆盖。
- 将代码库同步和模板创建接入三步向导。

### P2：发布批次

- 从矩阵创建发布草稿。
- 多环境/多集群目标选择。
- YAML/Helm Diff、Job 预览、审批和运行记录联动。

### P3：规模化体验

- 2000+ 服务的搜索、标签、收藏和保存视图。
- 构建缓存、制品复用、测试报告和实时日志。
- 金丝雀/蓝绿、自动回滚、变更日历和 AI 根因分析。

## 本轮验收

- 页面首屏不再以多个弹窗作为主要导航。
- 只拥有项目/服务只读权限的用户看不到编辑、同步、发布按钮。
- 只有测试和生产两个环境的项目，矩阵只显示这两个环境。
- 服务编辑可以明确看到基线 Revision、当前 Diff 和环境覆盖。
- YAML、Helm 和主机服务使用同一套服务目录和发布草稿入口。
- 页面文案通过 UTF-8 检查，新增页面不得出现乱码。
