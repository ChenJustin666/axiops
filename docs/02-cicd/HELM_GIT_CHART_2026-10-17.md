# 原生 Git Helm Chart：导入、修改与更新

推荐以 Git 维护 Chart 主线，AxiOps 固定 Commit 后保存版本，各环境单独保存 values 和所用 Chart 版本。平台允许修改 Chart，但另存为服务的自定义版本，不会自动提交 Git，也不会让其他环境自动升级。

## 首次导入

1. 在 Helm 项目中选择“仓库”，填写服务名称、代码源、仓库和分支。
2. 填写包含 `Chart.yaml` 的目录，例如 `deploy/chart`；Chart 就在仓库根目录时填写 `.`。
3. 系统自动读取这个目录内的完整 Chart，包括 `values.yaml`、`templates/`、`_helpers.tpl`、`values.schema.json`、其他配置文件及已展开的 `charts/` 子 Chart。遵循 `.helmignore`，不用逐个勾选文件。读取先固定 Commit，不混用读取期间变化的分支内容。
4. 完成导入后，在“服务与配置”选择服务及目标环境。左侧显示实际文件，点击后定位到对应 Chart 文件；“环境 values”用于维护此环境的参数。
5. 核对 Release 名称、集群、Namespace、环境 values 和镜像映射。标准 `image.repository` / `image.tag` 可直接使用；第三方 Chart 的键不同时按其真实 values 路径配置。
6. “预览与保存”检查渲染结果后保存。真正发布仍需执行工作流。

Chart 保留 Helm 自身的语法，如 `{{ .Values.service.port }}`、`include`、`tpl`、`range`，不会改写成 AxiOps YAML 变量。一个原生 Chart 可以包含多个资源和子 Chart，作为一个 Release 管理；需要独立升级、回滚的应用宜分别创建服务。

## Git 修改后同步

1. 进入已有服务的 Chart 配置，点击“检查仓库更新”；也可以右键服务，选择“从仓库导入”，更新的是当前服务。
2. 核对仓库、分支和 Chart 目录，点击“读取并比较”。左边列出新增、删除、修改的文件，右边并排显示平台最新 Chart 和 Git 内容。
3. 如果平台有自定义版本，先查看差异，再明确勾选使用 Git 内容另存新版本。旧版本仍保留。
4. 点击“导入为新版本”。只有文件发生变化时才能导入；Git Commit 或平台版本在比较后变化，会阻止提交，要求重新比较。
5. 在目标环境选择刚导入的 Chart 版本，检查该环境 values，预览并保存，再执行发布。测试、生产的 values 和已有版本不会因为 Git 导入而一起被替换。

导入只发生在主动操作时，本轮没有增加 Webhook 自动同步、自动发布或向 Git 推送的功能。

## 在平台修改

选择 Chart 文件 →“编辑 Chart”→ 修改/新增/删除文件 →“保存为自定义版本”。保存的是当前服务的 Chart 版本，与共享模板库和其他服务分开；当前环境还需预览保存后再发布。

日常副本数、CPU/内存、域名、Nacos 等差异，优先在选定环境的 values 修改。Chart 实现了哪些键，values 才能控制哪些行为。Secret 使用目标环境的引用，避免把密码、SK、Token 写入 Git 或明文 values。

若平台修改需要长期维护，建议把同样的修改通过正常代码评审合入 Git，然后重新比较同步。平台不会替用户直接提交或覆盖仓库。

## 当前兼容范围

- Helm v2 application Chart，目标 Namespace 内的应用资源。CRD、集群级资源不由当前发布链路接管。
- 支持 UTF-8 文件和已经展开的子 Chart。`.tgz` 二进制依赖包暂不直接导入，请先将依赖展开到 `charts/<chart-name>/` 并提交；缺少依赖会阻止导入，不会在部署时临时下载浮动依赖。
- 最多 500 个文件、64 个目录，目录深度不超过 16；单文件最多 1 MiB，序列化快照最多 4 MiB。软链接和 Git submodule 不跟随。仓库读取最多 2 分钟；超时不会创建 Chart 版本。
- 平台 Chart 编辑沿用现有模板默认值渲染校验；需要外部 values 才能通过 `required`/schema 校验的第三方 Chart，当前建议从 Git 修改后同步，并在目标环境填写 values 后预览。
- 导入确认 Chart 结构及依赖完整，不代表应用已经可运行。服务镜像、实际环境参数、集群 API/控制器、网络和就绪状态仍由环境预览及真实发布检查确认。
