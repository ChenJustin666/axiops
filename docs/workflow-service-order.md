# 多服务构建与部署顺序

## 日常操作

1. 打开项目 → 工作流 → 执行工作流。目标环境、集群、命名空间来自工作流绑定，执行时核对。
2. 默认只选择一个服务。需要一起发布时，勾选多个服务，分别选择分支。
3. 使用服务旁的 ↑ / ↓ 调整本次部署提交顺序，例如 server 在上、gateway 在下。
4. 点击执行：创建一条运行记录，在同一页面查看各服务构建、部署日志和最终结果。

运行详情的流程节点和上方节点列表都显示独立耗时，点击“部署”节点查看准备、资源提交、Pod状态和就绪检查日志。小于一分钟显示秒，超过一分钟显示“分、秒”；运行中每秒计时，结束后不再增加。默认显示简洁日志，排查时可切换“详细诊断”。资源提交完成后仍会检查就绪状态；Pod Running不等于应用已Ready。

这次调整不修改保存的工作流。需要保存默认顺序时，在“编排”的“服务部署顺序”中调整并保存。含共享步骤或复杂跨服务依赖的工作流，继续按完整工作流执行，不能随意拆分。

## 执行原则

```text
server  构建/测试/推送镜像 ─┐
                          ├─ 全部成功 → 提交 server → 提交 gateway
gateway 构建/测试/推送镜像 ─┘              各自观察部署结果
```

- 每个服务分别生成镜像；独立构建可以并行，实际并发受构建资源及容量控制。不把多个服务编译产物混成一个镜像。
- 任一构建或测试失败，本批所有部署均跳过，避免已有服务先更新后才发现另一服务不能构建。
- 提交顺序只要求前一服务的部署操作已提交，或提交已明确失败。后一个服务不等待前一个 Ready；前一个部署失败也继续提交后一个。每个服务保留自己的日志、健康检查和结果，存在失败时整次运行最终为失败。
- Kubernetes 自己调度 Pod，因此提交顺序不保证容器实际启动的先后时间。应用依赖连接需要应用自身支持重连。
- 部署阶段可能部分成功，没有自动跨服务事务回滚。处理失败服务前先核对各节点结果。
- 代码检出/镜像信息按服务保存。本次未增加同仓库多分支强制固定同一 Commit 的能力。

## 部署到另一环境

打开绑定目标环境的工作流，选择“使用已有成功镜像（不构建）”，为每个服务明确选择成功构建。平台固定镜像摘要，使用目标环境自己的 YAML、变量和运行资源，不复制测试环境配置。当前该入口支持符合条件的 Kubernetes YAML 工作流；包含测试等其他步骤时以界面能力为准。

代码、Dockerfile 或编译参数有变化，需要重新构建；仅环境配置变化通常可以复用镜像。执行前会核对所有选择服务的目标环境配置，预检失败不会创建部分运行。

## 多模块 Maven 项目

CardScout 这类 reactor 工程，由 Maven 决定 common、business、server 等模块的编译依赖顺序。可按服务配置 `mvn -pl card-scout-server -am package -DskipTests` 等实际构建命令；不要用部署箭头代替 Maven 模块依赖。`-DskipTests` 仅为示例，是否跳过测试按项目规范选择。

当前没有新增“一次 reactor 编译、共享产物供多个镜像消费”的执行器；这是后续可以单独评估的性能优化。

## 设计参考与验证

- [GitLab stages](https://docs.gitlab.com/ci/yaml/#stages)：同阶段并行，后续阶段以先前阶段成功为前提。
- [Jenkins parallel](https://www.jenkins.io/doc/book/pipeline/syntax/#parallel)：支持并行阶段与独立失败策略。
- [Kubernetes Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)：资源提交与 rollout 就绪是两个阶段。
- [Maven reactor](https://maven.apache.org/guides/mini/guide-multiple-modules.html)：依赖关系决定模块构建顺序。
