# AxiOps 企业级 CI/CD 优化方案

更新时间：2026-09-06

本文把服务依赖、环境晋升、发布策略、细粒度权限、成本/合规/可观测性、大规模服务检索、变更日历和灾备演练纳入 CI/CD 的企业级演进路线。所有能力必须继续遵守“一次构建、多环境晋级、不可变制品、环境覆盖与服务基线分离”的基础规则。

## 1. 优先级原则

```text
交付正确性：依赖 -> 晋升 -> 发布策略 -> 回滚
治理安全性：权限 -> 合规 -> 审计 -> 变更窗口
运营效率：搜索分组 -> 成本 -> 可观测性 -> 灾备演练
```

第一阶段先完成会影响发布正确性的能力；成本和运营看板不能替代发布前校验和权限复核。

## 2. 服务依赖管理

### 2.1 依赖模型

服务依赖不是简单的备注，而是版本化、可校验的交付关系：

| 字段 | 说明 |
| --- | --- |
| `source_service_id` | 上游服务 |
| `target_service_id` | 下游服务 |
| `dependency_type` | runtime、build、test、data、network、optional |
| `version_constraint` | 兼容版本范围或 API 版本 |
| `environment_scope` | 仅开发/测试/全部环境 |
| `startup_order` | 是否要求先启动上游 |
| `health_gate` | 上游健康条件 |
| `contract_ref` | OpenAPI、protobuf、Schema 或测试契约 |
| `owner` | 依赖关系负责人 |

依赖图保存 Revision。服务被删除、项目权限变化或依赖目标不再可见时，不能静默删除关系；必须进入待处理状态并提示负责人。

### 2.2 工作流行为

- 构建阶段：build 依赖按 DAG 顺序或并行矩阵执行；无依赖的服务可并行。
- 测试阶段：契约测试、集成测试和端到端测试读取依赖服务的环境地址和已晋级 digest。
- 部署阶段：按拓扑排序生成部署批次；循环依赖阻止工作流保存。
- 环境更新：只允许把依赖服务提升到兼容版本；上游失败时默认阻止下游发布。
- 可选依赖：允许显式 `allow_failure`，但生产发布必须记录例外原因和审批。

### 2.3 页面

服务详情增加“依赖关系”标签页：上游/下游、依赖类型、当前环境版本、健康状态、契约测试和最近一次变更。发布前显示影响分析：本次服务变更会影响哪些服务、环境和负责人。

## 3. 环境晋升链

### 3.1 晋升链模型

环境晋升链由项目模板配置，而不是写死为开发、测试、预发布、生产：

```text
dev -> test -> stage -> prod
```

小项目可使用：

```text
dev -> prod
```

大项目可使用：

```text
dev -> test -> integration -> stage -> prod-canary -> prod
```

每条边都是一个 `promotion_policy`，定义来源环境、目标环境、允许的 artifact 状态、必须通过的测试、审批角色、变更窗口和超时。服务可以选择项目默认链，也可以在授权范围内绑定更严格的链。

### 3.2 晋升条件

晋升只引用同一 artifact digest/checksum，不重新构建。默认条件包括：

- 源 Commit、服务 Revision 和构建配置快照一致。
- 来源环境部署成功并达到健康门禁。
- 必需测试和安全扫描通过，未处于 quarantine。
- 依赖服务达到兼容版本。
- 变更窗口允许当前操作。
- 目标环境和集群权限通过。
- 生产环境具备审批记录。

页面显示晋级时间线、当前制品、已通过门禁、阻断原因和下一步审批人。

## 4. 发布策略增强

### 4.1 流量染色

流量染色用于把测试请求、租户、用户或请求头稳定路由到指定版本。能力按基础设施适配：

- Ingress/Gateway：基于 Header、Cookie、Query、权重路由。
- Service Mesh：基于 Istio/Envoy VirtualService 和 DestinationRule。
- 应用层：由服务自行读取 `X-Axiops-Release` 或租户标识。

发布页面配置“染色规则”时必须显示能力检测结果；没有 Gateway/Service Mesh 时，不显示不可执行选项。染色规则属于环境服务覆盖，必须版本化并参与 Diff。

### 4.2 自动回滚条件

回滚条件分为硬门禁和指标门禁：

| 类型 | 示例 | 默认动作 |
| --- | --- | --- |
| 硬门禁 | rollout 超时、Pod CrashLoopBackOff、探活失败 | 立即停止并回滚 |
| 资源门禁 | OOM、CPU throttling、调度失败 | 停止批次并告警 |
| 业务指标 | 5xx 比基线高 2 倍、P99 延迟超阈值 | 暂停或回滚 |
| 质量门禁 | 测试失败、扫描高危漏洞 | 禁止晋升 |
| 人工门禁 | 审批拒绝、发布窗口关闭 | 暂停，不自动重试 |

指标查询必须记录 Prometheus 查询、时间窗、基线、实际值和判定结果。自动回滚不能跳过权限和审计；生产自动回滚仍创建独立回滚运行记录。

### 4.3 发布策略参数

滚动、金丝雀和蓝绿统一使用：`prepare`、`deploy`、`observe`、`promote`、`rollback` 阶段，并分别保存策略版本。多集群支持并行、顺序和集群级金丝雀。

## 5. 细粒度权限

权限同时控制菜单、数据范围和动作：

```text
菜单可见
  -> 项目/服务/环境/集群/工作流数据范围
    -> 查看/编辑/运行/审批/发布/回滚/删除动作
      -> 具体字段策略（镜像、Secret、生产参数、策略）
```

建议新增或明确以下动作：

- `service:dependency:view/update`
- `artifact:promote/use`
- `environment:override:view/update`
- `deployment:strategy:view/update`
- `deployment:rollback`
- `workflow:template:apply/update`
- `change_window:override`
- `cost:view/export`
- `compliance:waive`

字段级规则示例：

- 开发只能修改开发/测试环境的非 Secret 覆盖。
- 测试可以运行测试工作流，但不能批准生产晋级。
- 运维可以发布和回滚已批准制品，但不能修改代码源 Token。
- 安全角色可以查看扫描结果和批准风险豁免，但不能直接部署。
- 生产镜像只能从已晋级 digest 选择，不能输入任意 tag。

所有授权必须由后端按项目、服务、环境、集群和工作流范围重新校验；前端隐藏按钮只是体验优化。

## 6. 成本、合规和可观测性

### 6.1 成本

成本中心按项目、服务、环境和集群聚合：CPU/内存请求与实际使用、Job 执行时长、镜像存储、日志存储、缓存占用和多集群资源成本。页面提供趋势、异常增长、闲置环境和高成本服务，不把估算值冒充账单值。

### 6.2 合规

发布前生成合规检查清单：镜像来源、漏洞等级、SBOM、签名/证明、许可证、Secret 扫描、变更单、审批人、发布窗口和回滚方案。高危项阻止晋升；风险豁免必须有原因、到期时间和安全角色审批。

### 6.3 可观测性

统一关联 `trace_id`、`project_id`、`service_id`、`artifact_digest`、`workflow_run_id` 和 `deployment_target_id`。运行详情链接到日志、指标、Trace、Kubernetes 事件和探活记录。平台自身指标包括队列等待、构建耗时、缓存命中率、部署耗时、回滚率和通知成功率。

## 7. 2000+ 服务搜索和分组

服务列表必须服务端分页和索引，禁止前端一次加载所有服务。建议支持：

- 业务域、团队、负责人、语言、标签、项目类型、集群和环境筛选。
- 我的服务、待发布、环境偏离、构建失败、测试失败、生产审批中、高成本服务等保存视图。
- 服务目录树按业务域/团队/仓库路径懒加载；搜索结果显示完整权限范围。
- 批量操作先显示服务数、环境数、目标数和预计 Job 数。
- 支持收藏、最近访问和 URL 查询条件分享，但分享链接仍需重新授权。

## 8. 变更日历

变更日历统一展示发布、回滚、扩容、环境创建/销毁、维护窗口和审批状态：

- 项目/环境/集群三种视图。
- 计划变更、进行中、成功、失败、取消、冲突标识。
- 变更窗口和冻结窗口；紧急变更需要 `change_window:override` 和原因。
- 日历事件关联 Workflow Run、artifact、审批人、影响服务和回滚方案。
- 发布前检查同一环境/集群是否存在冲突变更。

## 9. 灾备演练

灾备不是单独的文档任务，而是可执行的演练工作流：

1. 选择演练项目、服务、目标集群/区域和 RTO/RPO。
2. 校验目标集群、镜像仓库、凭据、数据备份和依赖服务可用性。
3. 使用已晋级 artifact 在备用环境部署，不重新构建。
4. 执行健康、流量切换、数据恢复和依赖验证。
5. 记录实际恢复时间、数据点、失败步骤、责任人和改进项。
6. 生成演练报告，未通过项阻止生产灾备状态标记为合格。

演练使用隔离环境和明确的破坏范围；不能直接把生产回滚或生产流量切换当成测试。

## 10. 实施阶段

### E1：交付正确性

- 服务依赖图、影响分析、循环检测。
- 可配置环境晋升链和制品晋级门禁。
- 依赖版本与健康门禁接入工作流。

### E2：发布治理

- 多集群目标批次。
- 流量染色能力检测。
- Prometheus 指标门禁和自动回滚。
- 字段级生产发布权限和风险豁免。

### E3：企业运营

- 成本中心、合规检查、SBOM/签名关联。
- 统一日志/指标/Trace 链接。
- 2000+ 服务搜索、保存视图和批量操作。

### E4：运维流程

- 变更日历和冻结窗口。
- 灾备演练工作流、RTO/RPO 报告和改进项。

## 11. 验收标准

- 一个服务依赖多个上游时，构建/测试/部署顺序由依赖图确定，循环依赖无法保存。
- 同一 artifact digest 能经过可配置晋升链进入多个环境，不重复构建；门禁失败能显示具体证据。
- 金丝雀或蓝绿发布只在目标集群能力满足时可选；指标超过阈值可自动暂停或回滚。
- 开发、测试、运维、安全角色对同一项目看到的菜单、服务、环境和动作不同，后端越权请求返回 403。
- 发布详情能关联 Commit、变更文件、构建配置、缓存、制品、环境、集群、日志、指标和审批。
- 2000+ 服务搜索在服务端分页，批量操作能预估构建/测试/部署目标 Job 数量。
- 变更日历能阻止冻结窗口内未经授权的发布；灾备演练能生成可审计报告。
