# 单服务回滚与执行账号

2026-10-15：页面、接口、执行器已接通。本文替代早期“仅设计、尚未接入页面”的说明。

## 日常操作

1. 打开项目的工作流 Job，在 `#N` 执行记录操作列点 **回滚…**。运行详情顶部也有入口；选中部署节点后可点 **回滚该服务**。
2. 明确选择一个服务，再选择其历史成功部署版本。多服务发布一次只回滚一个服务，不默认回滚全部。
3. 核对固定的目标环境、集群、Namespace，以及当前版本 → 目标版本的镜像、配置版本和字段差异。需要时展开完整配置对照。
4. 勾选确认后提交。系统在同一个工作流下生成新的 `#N · 回滚` 记录，原发布记录保留。查看新记录的执行人、日志、耗时和就绪结果。
5. 如果提交时断网，保留页面提示，点击 **核对提交结果**。刷新后再打开原记录的回滚窗口也能恢复原请求标识；不要另开一次回滚来猜测结果。

没有历史成功版本时，不能把构建成功但部署失败的记录当作回滚目标。多服务运行整体失败时，其中已经成功部署的服务仍有资格作为该服务的目标版本。当前已经是所选成功版本时，系统禁止重复回滚。

## 恢复的范围

- YAML：重放同项目、同环境、同服务的成功部署快照及不可变镜像摘要，不重新构建，不读取当前分支或最新标签。使用当前有效的镜像拉取凭据，并检查配套资源引用、Kubernetes dry-run，再提交并观察就绪状态。
- Helm：使用同一 Release 的历史成功 revision。执行前核对当前 revision、历史资源清单和镜像摘要；Helm 历史已清理或不一致时失败并说明原因。页面对照是资源清单及脱敏参数引用，不能冒充完整的历史渲染配置。
- 新回滚结果形成新的部署快照，后续配置发布和版本查询能够识别它。
- 本轮支持 Kubernetes YAML / Helm 的单服务回滚；主机部署不能套用此接口。

回滚不是数据恢复。数据库变更、PVC 内的数据、外部密码及外部系统状态不会还原。YAML 快照不保存并重建旧密码明文；历史配置中的 Secret/ConfigMap 引用必须在当前目标中仍有效。Helm 依其集群历史执行，需注意 Chart 中 Secret 与 hook 的实际行为。

当前配置编辑草稿不因回滚而被改写。回滚恢复运行版本；后续发布前应重新核对草稿与当前运行版本的差异。

## 防止误操作的约束

- 环境、集群和 Namespace 由后端固定，不允许在回滚窗口切换到另一环境。环境绑定发生变化，或同一 Namespace 被其他有效项目的活动环境重复绑定时停止回滚；已删除项目的历史环境不会误拦截同名项目重建。
- 预览、提交事务、Worker 执行前检查版本和绑定。打开窗口后版本变化，需要重新预览确认。同服务、同环境存在未完成发布或回滚时互斥；独立服务可继续发布。
- 请求有持久化幂等标识，重复点击、响应丢失后重试返回同一执行记录。Worker 使用稳定操作标识恢复，不能在发现更新版本后重放旧发布。
- 目标镜像必须包含完整 sha256 摘要。镜像仓库已经删除镜像、凭据失效、资源引用缺失或应用无法就绪时，任务会失败并显示原因；预检不能保证外部资源在执行期间始终可用。
- YAML 目标缺少当前的非 PVC 资源时停止，避免默默残留控制器或自动误删。额外 PVC 保留，并明确提示数据不会删除。
- 拦截其他服务也声明管理的 YAML 资源，以及被多个服务管理的同名 Helm Release。共享资源应明确归属，不能把一份全项目 YAML 放在每个服务中分别回滚。
- 原有生产/环境审批策略继续生效，页面会显示需要审批；此次不新增或取消审批机制。
- 执行人来自认证账号，保存账号 ID 与执行时名称，前端不能指定执行人。历史无名称快照时按原账号读取，账号不存在则显示账号 ID。

这些约束覆盖平台内的操作。外部 kubectl、其他发布平台或应用自身的数据/接口不兼容仍需运维流程约束，不能宣称 Kubernetes 多资源更新或多服务回滚具有整体事务性。特别是 Helm hook、数据库迁移和共享存储，应在发布设计中单独评估。

## 验证与当前数据

验证使用隔离的临时 MySQL 库、假的集群 Provider 和浏览器拦截提交，覆盖部分成功、多服务单选、跨服务/环境拒绝、绑定变化、资源归属、镜像摘要、并发互斥、过期预览、幂等提交、Worker 恢复、失败依赖和断网后刷新核对。没有对业务服务执行真实回滚。
