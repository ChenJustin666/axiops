# Helm 多环境配置使用步骤

本版参考 Zadig v5.0 的环境 values 流程。Chart 是服务的公共源码版本；每个环境独立保存 values。保存配置后，再通过工作流发布。

## 新项目和新环境

1. 在 Helm 项目中，通过模板或代码仓库创建服务。Git 导入填写 Chart 目录；可以包含原生模板、辅助文件和已准备好的依赖。
2. 创建环境，明确环境名称、集群与 Namespace。生产环境需要开启生产标识；环境名称不自动决定 Spring Profile 或 Nacos namespace。
3. 在同一页面的“配置此环境的服务”选择已有服务。每个服务使用固定的 Chart 版本，分别编辑环境 values。默认 `{}` 表示继承 Chart 默认值，不会把默认参数全部复制成固定覆盖。
4. 可直接粘贴完整 values，也可只写差异；“导入 values”支持固定 Chart 内的 YAML 文件、独立 Git 仓库文件、参考已有环境。参考环境复制的是服务环境覆盖，目标共享配置和凭据独立维护。
5. 点击“预览并创建环境”，检查每个服务的“最终 values”和“渲染 YAML”。生产环境需要明确确认。确认后，环境和所选服务配置一起保存；任一校验失败则整次创建回滚。
6. 进入该环境的工作流发布。配置预览使用校验镜像占位值，实际镜像由工作流选定的构建制品注入；预览不是实际运行资源。

也可不选择服务，先创建空环境，之后进入服务配置，选择该环境保存服务配置。初始化中多环境逐个创建，已成功的环境可在下次继续初始化时复用。

## 日常修改测试 / 生产配置

服务与配置 → 选择环境 → 选择服务 → 默认进入“当前环境 values”。只有选择“Chart 源码”或具体 Chart 文件时，才进入公共源码编辑。

以下是 Sinozo Java 模板的环境覆盖示例，地址和 namespace ID 必须按真实环境填写：

```yaml
service:
  port: 28080
  replicas: 1
resources:
  requests:
    cpu: 100m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 1Gi
application:
  profile: test
nacos:
  enabled: true
  serverAddr: nacos-test.internal:8848
  namespace: your-test-namespace-id
```

生产环境独立填写副本、资源、Profile、Nacos、域名等值。修改测试配置不会同步生产，也不会修改模板库。

点击“预览与保存”，检查最终合并值和 YAML 后保存。保存成功显示发布后生效，随后执行工作流。生产环境继续优先使用已经验收的镜像制品；不要把配置草稿当成运行版本。

## 环境共享 values

入口：环境配置 → Helm 共享 values。服务 values 编辑区也提供快捷入口。

共享值只作用于当前环境。建议只放各服务 Chart 使用相同结构的公共参数；不同 Chart 是否接受这些参数，以全体服务校验结果为准。

优先级从低到高：

1. Chart 默认 values。
2. 既有项目、服务、环境的路径变量（兼容已有配置，不自动迁移）。
3. 当前环境共享 values。
4. 当前服务在当前环境的 values。
5. 发布时受控注入的镜像制品。

修改共享值后先“校验影响范围”，查看各服务最终 values 的前后对比；自身覆盖了共享值的服务可能不受影响。任何权限、配置或并发版本校验失败，都不会部分保存。保存不会自动部署。

密码、SK 等使用安全凭据绑定或目标 Namespace 内的 Secret 引用。共享值和普通 values 不能覆盖已绑定的凭据路径；预览对凭据内容脱敏。

## Git values 文件更新

Chart Git 来源与环境 values Git 来源分别管理，可以使用不同仓库、分支和目录。

1. “导入 values → 代码仓库”选择代码源，填写仓库路径、分支/Tag/Commit 和 YAML 文件相对路径。
2. 读取文件并应用到草稿，再预览保存。平台保存来源 Commit 和导入基线。
3. 平台上可继续编辑 values，不会自动推送 Git。
4. Git 有更新时点击“检查更新”。系统比较上次导入内容、当前平台内容和新 Git 内容。互不冲突的修改自动合并；相同参数冲突需要逐项选择保留平台或采用 Git。数组整项处理，不按下标拼接。
5. 应用到草稿后，再预览保存。新导入来源若在提交前发生分支移动，会拒绝陈旧提交，需重新读取比较。已保存的旧快照仍可在平台独立修改，不要求 Git 分支永远不动。

Chart 检查更新不会顺带覆盖环境 values，values 更新也不要求升级整个 Chart。

## 测试同步到生产

先保存源环境，再“同步到其他环境”，选择目标和具体参数路径，例如 `resources.limits.memory`。未勾选的生产 CPU、域名、HPA/PDB 等配置保持目标原值；数组作为一项整体替换。目标镜像路径映射、凭据和 Git 来源保持独立。

同步界面提供的是源环境显式覆盖项。清除目标覆盖以恢复继承，可直接在目标环境 values 中删除对应键。不要用 `null`、空字符串或删除互相代替；最终含义由 Helm 合并和 Chart 模板决定，必须检查预览。

生产保存前检查差异并确认，之后按目标环境工作流发布。配置同步不会触发部署。

## 原生 Chart 编辑

“Chart 源码 → 编辑 Chart → 保存为自定义版本”会检查目录、元数据、文件摘要、依赖和模板语法。不会执行 `lookup`，也不会要求所有环境参数已写进默认 values。

保存新公共版本后，选择该版本并预览当前环境；此时再校验 schema、required、渲染结果和目标 Namespace。其他环境不会自动升级。模板库修改仍在模板库操作。

## 验证范围

本版的自动化测试覆盖多环境隔离、默认值继承、最终 values 脱敏、共享优先级与冻结快照、并发版本拒绝、Git 来源校验与三方合并、深层参数同步、创建环境回滚和生产确认。

相关前端 119 项测试、修改文件 ESLint、后端相关测试与隔离 MySQL 集成测试、最终 Vite 生产构建通过。整仓类型检查仍有 1296 条既有诊断，本轮修改文件未发现诊断；不表示整仓检查全部通过。

浏览器工具当前没有连接到可控窗口，实际视觉点击尚未验收；本轮未执行真实集群发布。任意第三方 Chart 的运行成功，还取决于应用镜像、Secret/PVC、控制器、网络等真实条件。

本版保留原生 values 编辑，未新增任意 schema 自动表单、后台 Git 自动同步或 Git 回写；后续按使用反馈调整。
