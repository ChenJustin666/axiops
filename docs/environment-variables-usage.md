# 环境变量配置与日常使用

这里的“全局变量”是当前环境内共享的模板变量，不是所有项目或所有环境的全局设置，也不是自动写入容器进程的环境变量。

| 配置位置 | 用途 | 生效范围 |
| --- | --- | --- |
| 服务配置→共享模板→默认变量 | 保存通用默认值和YAML结构 | 采用该模板版本、未被覆盖的环境 |
| 环境→选择环境→全局变量 | 同环境多服务共用值，例如APP_PROFILE、公共域名 | 当前环境中引用它且无服务覆盖的配置 |
| 服务配置→选择服务和环境→变量与来源 | 某服务在某环境独立配置，例如端口、副本数 | 当前服务、当前环境 |
| 环境→环境资源配置 | ConfigMap、Secret、PVC等资源定义 | 目标环境的后续YAML部署 |

普通YAML变量优先级：服务环境覆盖 > 环境共享变量 > 模板默认值。历史replicas字段存在时也有覆盖作用，服务配置中显式修改或恢复继承会清除此旧覆盖。Image、Namespace、Service等由系统提供，不使用同名普通变量。

变量必须被引用才有作用。例如设置APP_PROFILE=qa、port=8080后，Deployment容器可以写：

```yaml
containers:
  - name: app
    image: {{.Image}}
    ports:
      - containerPort: {{.port}}
    env:
      - name: SPRING_PROFILES_ACTIVE
        value: "{{.APP_PROFILE}}"
```

`containerPort`只是Kubernetes声明的容器端口，不会自动修改Java程序监听端口；程序端口需要同时通过其配置文件/启动参数或环境变量设置。普通字符串按YAML规则使用引号，部署前预览渲染结果。

密码不要使用普通变量：YAML采用目标命名空间中的Kubernetes Secret，并在Deployment中通过secretKeyRef或envFrom引用。全局变量里的加密凭据引用目前用于Helm values，不会自动插入YAML。Helm普通变量使用实际values路径（例如replicaCount、image.repository），以Chart模板是否引用为准。

日常流程：

1. 多服务共用值改“全局变量”；只改一个服务用“服务配置→该环境”。观察来源，避免服务覆盖使共享值看起来没有生效。
2. 看保存前后差异，再保存。全局变量支持撤销、未保存关闭提醒、生产确认；加载失败或响应范围不匹配禁止保存。保存共享值不会改变其他环境。
3. 服务配置切换“代入环境变量”查看渲染；需要跨环境更新用“同步到其他环境”，选择字段和目标后预览。共享变量不会自动批量复制到其他环境。
4. 重新提交目标环境的部署工作流。已提交任务冻结了当时输入，之后修改变量不会改变已有任务。单独保存配置不会修改集群。
5. 环境→运行资源→查看实际YAML、Pod状态与日志，确认目标命名空间和实际配置。应用是否采用新值仍须核对日志/健康状态。

ConfigMap/Secret通过env或envFrom注入时，已有Pod不会自动更新进程环境，需要重建Pod；挂载文件的更新与应用自动重载也不是同一件事。当前不能声称AxiOps修改ConfigMap后会自动重启服务，应通过包含Pod模板变更的发布来更新Pod。

“待保存变更”是本次配置差异；“资源预览”是部署前与集群资源的对比，二者都不是部署成功证明。独立工作流详情页原有“变更”按钮目前仍是未接通入口，不可作为历史配置审计使用。
