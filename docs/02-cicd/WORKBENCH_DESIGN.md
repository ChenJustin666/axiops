# CI/CD 交付工作台设计

更新时间：2026-09-06

## 决策

采用“项目为业务边界，环境为逻辑发布面，服务为可复用交付单元，目标为具体集群部署位置”的模型。不要把一个集群直接等同于一个环境，也不要为每个环境复制一套服务和构建 Job。

```text
项目
├── 服务基线（代码、构建、定义、默认镜像、默认策略）
├── 环境（dev / test / stage / prod，可选）
│   └── 发布目标（一个或多个 cluster + namespace / host group）
├── 环境服务覆盖（版本、镜像、变量、副本、发布策略）
└── 工作流模板与运行记录
```

`服务基线` 是唯一的服务定义。`环境服务覆盖` 只保存相对基线的差异。一个逻辑生产环境可有多个发布目标，例如 `prod-cn-sh`、`prod-cn-bj`；一次发布把同一个不可变镜像 digest 分发到多个目标，但每个目标拥有独立状态、日志和回滚点。

## 用户工作流

### 1. 创建项目：少填字段，先生成可用基线

项目向导只有三步：

1. **项目与交付类型**：项目名称、编码、项目类型（YAML/Helm/主机）、所属团队、默认镜像仓库。
2. **服务导入**：选择公共代码源、仓库、分支和根目录；自动识别同级服务目录、语言、Dockerfile、YAML/Chart 和镜像字段。用户只确认识别结果，允许跳过暂不发布的服务。
3. **环境蓝图**：选择预设 `开发-测试-预发布-生产`、`开发-测试` 或空白；为每个环境选择一个或多个目标集群和 Namespace 规则。

系统自动生成：

- 镜像名：`{registry}/{project-code}/{service-code}`。
- Namespace：`{project-code}-{environment-code}`，用户可覆盖。
- 默认构建模板：由语言和 Dockerfile 识别推荐，例如 Go、Maven、Node.js、Python、前端静态站点。
- 默认部署策略：开发/测试滚动；预发布滚动或金丝雀；生产由项目模板预设滚动、金丝雀或蓝绿。
- 默认工作流：`构建 -> 测试 -> 部署 -> 通知`；生产自动插入审批。

必须由用户确认的字段仅包括：项目类型、代码源/仓库、服务目录、至少一个环境目标、生产策略和团队负责人。语言、框架、镜像名、Dockerfile、构建命令、服务端口、Kubernetes 资源和镜像替换点均可自动识别后再确认。

### 2. 新增或克隆服务

新服务有三种入口：从代码库同步、手工/模板创建、克隆已有服务。

克隆不会复制运行记录和 Secret：选择源服务后，只需修改服务名、代码目录、镜像名，并勾选要继承的环境覆盖。系统复制构建模板、资源默认值、健康检查、发布策略和非敏感变量；需要用户重新选择或确认代码目录、凭据引用和 Secret。

对于“3 后端 + 2 前端”的项目，推荐从仓库根目录批量导入五个服务。在向导的预览页逐项显示识别语言、构建方式、镜像和 YAML/Chart 目录，允许一次确认全部服务。

### 3. 日常配置与发布

服务定义更新和环境更新分开：

- 服务页编辑基线：代码路径、YAML/Chart、构建配置、默认资源、默认镜像、健康检查。每次保存形成新的服务 Revision。
- 环境页编辑覆盖：目标 Revision、镜像 digest、变量、副本、HPA、策略和目标集群。保存为草稿，不自动发布。
- 发布页选择环境和一个或多个服务，预览资源/values Diff 后才创建运行。

## 页面设计

### 项目工作台

项目内导航固定为：`概览 | 服务与环境 | 工作流 | 运行记录 | 制品 | 变量与模板 | 设置`。

“服务与环境”是默认页：左侧为服务分组和逻辑环境；中间是环境服务矩阵；右侧是选中服务在当前环境的发布草稿。这个结构比“先进入服务，再单独进入环境”的方式更适合日常发布，因为用户真正关注的是“某环境中某服务当前运行什么版本、下一次要改成什么”。

### 服务与环境矩阵

表格每行代表一个服务在当前环境中的有效部署状态：

| 列 | 展示内容 |
| --- | --- |
| 服务 | 名称、分组/仓库目录、负责人、服务类型 |
| 当前版本 | 服务 Revision、Commit、构建编号、镜像 digest |
| 目标 | 集群、Namespace、Release/工作负载、实例数 |
| 策略 | 滚动、金丝雀、蓝绿，及阶段参数 |
| 状态 | 健康、最近运行、待发布/失败/审批中 |
| 操作 | 编辑基线、编辑环境草稿、Diff、发布、回滚 |

切换环境后矩阵不改变服务基线，仅切换到该环境的覆盖和目标。若环境有多个集群，同一服务以可展开的目标行显示；默认显示汇总状态，避免 2000+ 服务时表格膨胀。

### 服务详情

服务详情使用三栏布局：

```text
Revision/文件树 | YAML/Helm/主机配置编辑器与 Diff | 组件、镜像、构建、健康检查、环境覆盖
```

底部是 Revision 历史、代码同步状态、环境引用和审计记录。编辑基线后，环境不会立即变化；用户在环境页选择新 Revision 后才进入发布草稿。

### 工作流与 Job

不要把每个环境的“构建 Job”永久化。构建是服务 Revision 的产物生成过程：同一 Commit/构建配置只构建一次，产出镜像 digest 或制品 checksum。部署、测试、通知、审批才按环境和目标生成运行时 Job。

```text
选择服务
 -> 并行构建（每服务一个 build job）
 -> 并行测试（按服务或测试套件）
 -> 部署环境
    -> target A: deploy job
    -> target B: deploy job
 -> 通知
```

因此运行详情同时显示：服务构建 Job、测试 Job、每个环境目标的部署 Job、审批和通知 Job。用户可从环境服务矩阵直接跳到对应运行或目标日志。

## 发布策略

策略属于“环境服务覆盖”，默认继承项目或服务策略：

- **滚动发布**：副本、maxSurge、maxUnavailable、等待时间、失败自动暂停。
- **金丝雀发布**：阶段流量/副本比例、观测窗口、Prometheus/SLO 判定、人工确认或自动推进。
- **蓝绿发布**：preview 与 active target、流量切换、验证窗口、保留旧版本时间。

是否允许某策略由资源能力决定：YAML/Helm 项目需要有 Service/Ingress/Gateway 或服务网格接入；否则前端不显示不可执行的金丝雀/蓝绿，而不是让用户填写无效参数。

## 规模与权限

2000+ 服务不能默认使用全量服务树。项目内按团队、领域、标签和负责人筛选；服务矩阵服务端分页，支持“我的服务”“待发布”“失败”“本环境已偏离基线”等预设视图。批量操作永远显示选中服务数和影响环境/目标数。

权限按项目、服务、环境、集群和工作流范围叠加。开发人员看到自己负责服务的基线、测试/开发环境和只读运行日志；测试人员可修改测试环境草稿和运行测试工作流；运维才能处理生产目标、审批、发布策略和回滚。

## 交付顺序

1. 确认项目初始化向导、环境目标模型和服务环境矩阵的视觉设计。
2. 重构前端工作台与服务详情，不新增数据库字段。
3. 增加同级目录多服务导入、自动识别和服务克隆。
4. 增加环境目标多集群和环境发布草稿；此项需要评估并增加迁移。
5. 增加策略参数、工作流运行目标扇出、真实测试集群 E2E。
