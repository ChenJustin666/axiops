# YAML 服务配置的环境切换与同步调研

> 2026-09-29 更新：用户已授权实现，新增环境切换、加入/选择性同步、事务冲突保护和运行配置快照。本文保留为当时的调研记录；当前实现与 Windows Application Control 启动阻塞见 [服务环境配置](service-environment-configuration.md)，不要将下方“未实现”当成当前代码状态。

日期：2026-09-25。范围：当前 AxiOps 代码的服务编辑、环境变量、服务版本、预览和工作流执行链路。本轮为代码调研与设计建议，没有新增功能、同步业务配置或触发部署。

## 结论

用户需要在同一个服务配置页面保留服务和文件选择，切换测试、预发、生产环境，查看实际配置；修改配置后可以选择同步目标环境。当前只具备部分数据模型和分散入口，尚未形成完整功能。应先统一版本选择与环境配置解析，再实现环境切换和有差异预览的同步。

| 能力 | 当前实现 |
| --- | --- |
| 共享 YAML 模板、保存新版本 | 支持，写入 service_revision，并更新 app_service.current_revision_id |
| 同一服务在不同环境使用不同变量 | 有环境服务变量 API；初始化环境页有编辑入口，上一轮补齐了 YAML resolver 对该变量组的读取 |
| 在服务 YAML 编辑页切换环境 | 未实现；该组件只读取服务 revision，没有选中环境状态和环境变量加载逻辑 |
| 保存配置后同步到已有多个环境 | 未实现，没有批量目标选择、差异预览与提交接口 |
| 每个环境固定一个服务版本 | 数据模型和保存 API 存在，前端服务覆盖面板被 v-if=false 隐藏；执行链路未统一采用此绑定 |
| 环境克隆 | 仅新建非生产环境，复制部分数据；不能当作已有环境间同步 |
| 预览部署资源变化 | 有后端 dry-run 预览能力，但其默认版本选择规则与执行入口不一致 |

## 代码证据与当前问题

1. `axiops-web/src/views/cicd/project-workspace/components/ServiceWorkbenchPanel.vue`：加载服务 revisions，默认展示最新 revision；保存创建服务公共版本。`加入环境`传入 `environments[0]`，不是用户当前选择的环境，也没有保持当前服务传入环境弹窗。
2. `project-workspace/index.vue`：初始化环境页的 `selectEnvironment`、`loadEnvironmentServiceVariables`、`saveEnvironmentServiceVariables` 支持逐环境服务变量；日常环境页偏向运行资源，没有复用相同编辑体验。环境弹窗接受单个 environment，没有环境选择器，打开时又默认选择第一个服务。
3. 同文件的环境服务变量加载仍插入硬编码默认值：port=8080、replicas=2、cpuLimit=500m、memoryLimit=512Mi。接口报错时还用默认数据兜底。该路径与上一轮修复的服务工作台是不同入口，仍待修复。它可能将展示用默认值误保存成环境覆盖。
4. 环境服务变量缓存仅按 service_id 索引，异步请求未校验环境切换序号；快速切换时，旧请求可能回填另一环境的变量组。保存使用缓存中的 set.id，存在“当前显示环境与实际保存目标不一致”的风险。这是代码路径判断，本轮未声称完成浏览器复现。
5. `internal/cicd/appsvc/repository.go:CreateRevision` 只更新服务 current_revision_id，不更新既有工作流节点或每个环境的绑定版本，也不执行部署。
6. `project-workspace/index.vue:confirmWorkflowExecute`：选择服务执行会传入服务 current_revision_id；按工作流配置执行则保留节点中已保存的 service_revision_id。因此保存新模板后，两种入口可能使用不同版本。
7. `internal/cicd/deploypreview/repository.go:ResolveTarget` 的版本选择为显式版本 → 环境绑定版本 → 服务当前版本；`internal/cicd/workflow/yaml_resolver.go:LoadYAMLSource` 使用工作流节点传入的 revisionID，只从 environment_service_override 读取镜像、副本数，没有采用其 service_revision_id。不能在此处直接无条件切换为环境版本，否则已排队运行会悄悄换版本；应在提交运行时统一解析并冻结。
8. `internal/cicd/projectenv/repository.go:Clone` 只复制环境全局普通变量与 service_override，未复制环境服务变量组和环境专属资源；`projectenv/logic.go:Clone` 只接受非生产来源且新环境固定为非生产。它不是跨已有环境同步的替代实现。
9. `workflow/yaml_resolver.go` 在执行时读取环境变量、镜像覆盖、副本数和专属资源。因此即使服务 revision 固定，构建期间修改环境配置仍可能影响该次后续部署；新设计应冻结配置版本和可重放内容，避免预览与执行不一致。

## 推荐交互

服务配置页顶部保留服务名称，增加环境选择：`共享模板 / 测试环境 / 预发环境 / 生产环境`。同一服务同一文件切换，不跳回第一个服务。环境数量多时使用下拉搜索，名称旁显示生产标识。

- **共享模板**：编辑公共 YAML 和默认变量，保存生成新版本；显示哪些环境正在使用旧版本。
- **某个环境**：显示环境名、集群、Namespace、目标模板版本与已部署版本。默认展示该环境最终 YAML 的只读预览，以及可编辑的环境覆盖；每个变量标明来源（模板、全局、服务覆盖），支持“覆盖”和“恢复继承”。缺失值直接标红，不填入猜测值。
- 修改 YAML 结构明确进入共享模板编辑；环境页首先支持变量覆盖，避免每个环境维护一整份 YAML。确需结构差异时作为后续显式 patch 能力，不能把整份渲染结果反存为公共模板。
- 按钮明确区分“保存当前环境”“同步到其他环境”“部署”。保存和同步更新配置，部署通过已有工作流执行。
- 切换环境时保留当前文件与服务，处理未保存更改；缓存使用 environment_id + service_id，取消或忽略过期请求。加载失败展示原因并禁止用默认数据覆盖已存配置。

## 同步语义

| 同步内容 | 建议默认行为 |
| --- | --- |
| 共享模板新版本 | 可选择多个目标环境，切换其目标 revision，保留各环境覆盖值 |
| 指定普通变量 | 单独勾选变量和目标，预览新增 / 修改 / 删除；未勾选的值保持不变 |
| 继承的默认变量 | 保持继承，不复制成显式环境覆盖；新模板新增必填变量时按目标提示缺项 |
| 集群、Namespace、环境身份 | 不属于配置同步内容，按目标环境原绑定渲染 |
| 域名、Nacos 地址、数据库配置、副本数 | 默认保留目标值；确需同步时显式选择，并展示差异 |
| 凭据 | 不复制明文，引用必须满足目标权限与作用域；不默认批量同步 |
| 环境专属 Ingress / ConfigMap / PVC | 作为独立资源操作，不随服务模板默认同步；引用一致性需预检 |

例子：测试环境 risk_server 把 port 修正为 8001，选择只同步 port 到预发、生产；生产已有 replicas=3，仍保留 3。若只是模板新增探针，则同步模板版本，生产端口和其他环境覆盖仍按生产配置渲染。

提交前列出每个目标的模板版本变化、变量差异、渲染问题；目标默认不全选。同步成功明确显示“配置已保存，待部署”，不能显示“发布成功”。

## 实现顺序与验收

1. **统一解析**：共享预览与运行提交的版本解析器，明确显式运行版本和环境目标版本的关系，停止单服务执行时无提示强制选择服务最新版本。提交时冻结选定 revision、环境配置修订与镜像策略；worker 使用本次运行已解析的输入，实际部署前仍做必要校验。
2. **环境切换入口**：服务页接入 environment/service 变量和绑定；移除初始化页面的虚构默认值与失败兜底，处理未保存内容、过期请求和真正的权限/404状态。
3. **同步预览与提交**：同项目目标权限检查；先生成包含源与目标修订号的差异计划，再按预期 revision 提交。配置批次在数据库事务内保存，冲突或校验失败返回具体目标且不部分覆盖；加幂等键和变更记录。集群部署仍独立执行并遵守环境已有审批策略。
4. **验证场景**：同服务环境隔离、切换时慢请求、加载失败、模板继承与显式覆盖、只同步 port 保留生产 replicas、目标被他人修改时拒绝覆盖、新增变量缺值、跨项目/无权限目标拒绝、预览与执行使用相同版本、保存同步不触发构建/Apply、构建期间改配置不改变已提交运行。

现有 service_revision、environment_service_override、variable_set、deployment_snapshot 可复用；需补同步计划/修订历史和运行配置冻结能力。不是仅增加一个下拉框和复制按钮就能完整支持。
