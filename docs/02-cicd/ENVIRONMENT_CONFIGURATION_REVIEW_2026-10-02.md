# 环境配置与发布体验重新评估

日期：2026-10-02。状态：**第一版已实现并完成浏览器验收；高级能力仍按本文边界保留**。

本次回应“使用习惯不同，需要重新评估哪种方案最好”。本文件是 CI/CD 模块的专项评估和第一版交接记录；操作步骤见本文“第一版交付”及 `../build-and-environment-delivery.md`。本轮已修改环境配置、发布和前端工作台代码，未触发真实业务构建或生产部署。

同日补充：用户明确要求整份 YAML 新增/修改，以及 env 等日常配置快速发布。**整份环境 YAML 编辑已作为阶段一基本交付能力完成**，模板只作为起点，不限制后续 YAML 内容。

## 第一版交付

- 服务配置按“服务 + 环境”隔离。当前环境可直接编辑整份 Kubernetes YAML，多文件使用 `---` 分隔并保留文件名索引；右键可新增 YAML 文件。
- YAML、变量、ConfigMap/Secret 引用、Ingress、PVC 和 CPU/内存覆盖通过同一个“预览与保存”提交。后端统一校验 YAML、命名空间、资源重复、环境归属、凭据权限和并发 token。
- 测试、生产保存互不覆盖。生产保存需要勾选目标、差异和镜像确认；并发冲突时保留编辑草稿，不自动覆盖他人的新版本。
- 配置发布使用当前环境最近一次完整成功部署的不可变镜像摘要，携带环境 ID、配置摘要和部署快照；不自动重新构建、不拿最新构建替换镜像，也不携带分支。
- 已有 ConfigMap 被工作负载引用时，配置变更会生成受管 hash 触发 Pod 模板滚动；未引用的 ConfigMap 不会无故滚动其他工作负载。
- 真实浏览器验收脚本为 `local/dev/browser-check/environment-workbench-v1.cjs`，本轮结果：登录和只读 API 正常、页面无 JS 错误、HTTP 5xx 为 0、业务写入为 0；截图保存在 `local/dev/browser-check/environment-v1-*.png`。脚本中的写入均为受控路由模拟，不会写入业务数据库或集群。

### 测试步骤

1. 打开 `http://127.0.0.1:3006/`，进入项目 → 服务配置，选择具体服务和目标环境。
2. 在 YAML 编辑器修改整份内容，或在左侧服务文件目录右键新增 `configmap.yaml`、`ingress.yaml` 等文件。
3. 切到“CPU / 内存与配套配置”，只填写当前环境需要覆盖的值；留空表示继承 YAML，单位使用 `Mi` / `Gi`。
4. 点击“预览与保存”，检查修改前/后 YAML、目标 Namespace、变量来源和资源差异，再保存。
5. 测试环境保存后切换到生产，确认生产内容没有被带入；生产保存必须显式确认。
6. 当前环境已有成功部署后，使用“保存并发布”验证仅配置发布。它保留原镜像并走现有工作流、审批、就绪检查和日志链路。

### 当前边界

- 任意复杂 YAML 的三方合并、完整 GitOps 回写、Helm 与主机发布的统一编辑语义仍未完成。
- 配置保存只代表配置版本已校验并保存；必须经过工作流发布后才会影响集群，不能据此判断应用已健康。
- 没有完整成功部署镜像摘要的环境不能使用“仅配置发布”，需要先进行一次明确镜像发布。

## 1. 推荐结论

推荐：**按服务、按环境两个入口，共用一个服务环境配置工作台；保留 YAML，常用项提供轻量表单；统一完整预览、保存和发布。**

环境仍是部署目标的唯一来源，服务定义仍可来自模板、仓库或手写 YAML。日常操作先看清“哪个服务、哪个环境、改了什么”，无需先理解变量组、配套资源和内部覆盖层级。底层继续复用环境隔离、版本绑定和运行快照。

不是所有人必须使用表单，也不是为每种习惯维护一套独立配置。决定写入位置的是字段归属；不同入口显示并修改同一个对象。Git 管理作为后续可选能力，不在这轮把现有仓库导入误称为完整 GitOps。

## 3. 方案比较

| 方案 | 适合的习惯 | 主要代价 | 本项目选择 |
| --- | --- | --- | --- |
| 每环境复制一整套 YAML | 直接编辑文件的熟练用户 | 公共改动重复修改，环境长期漂移，秘密和地址容易复制错 | 保留显式环境专用定义的可能，不作为默认路径 |
| 全部做表单，隐藏 YAML | 对标准应用进行重复操作 | 表单覆盖不完任意资源，复杂 YAML 转换可能丢字段，维护成本高 | 不采用 |
| Git 为唯一写入来源 | 已建立 Git 审核及发布习惯的团队 | 小修改也需提交；需具备分支权限、回写、同步和冲突处理 | 后续独立模式，不强制当前用户迁移 |
| **统一工作台＋公共定义与环境差异＋表单/YAML互补** | 同时包含开发、运维和 YAML 用户 | 需要明确字段归属和合并规则，并提供可信的完整预览 | **推荐** |

判断优先级：环境隔离与预览可信 > 常用操作少步骤 > 不同习惯可用 > 页面入口数量。不能靠藏掉 YAML 或增加更多弹窗解决问题。

## 4. 页面与导航

两个入口解析到同一个 `项目 + 服务 + 环境` 上下文：

- 服务与配置 → risk_server → 测试/生产。
- 环境 → 测试环境 → risk_server → 配置。环境首页仍以真实运行资源为主。

顶部紧凑显示：服务名称、环境选择、集群/Namespace、配置状态；环境较少用标签，较多时用可搜索下拉。生产标识同时使用文字与颜色。切换环境不会保存或执行任何变更，有未保存内容时才提示。

左侧沿用服务/文件目录。中间保留 YAML 大编辑区、多文件同页、`---`、文件名和点击定位 `kind:`。常用配置通过紧凑页签或侧栏进入；CPU/内存不再藏在长页面底部。新增文件和导入继续留在目录菜单，不重新堆到编辑器顶部。

建议内容入口：

- **常用配置**：副本、明确选定容器的 CPU/内存，已有变量的最终值与来源。不能无条件为每个服务添加资源、域名或存储。
- **YAML / 文件**：模板结构、ConfigMap、Ingress、PVC 等；继续支持模板导入和手动创建。旁边标明“编辑公共定义”或“编辑当前环境差异”，不能靠上下文猜测保存范围。
- **差异与历史**：对比其他环境、对比上次发布、配置修改记录。

“最终 YAML”是明确的预览动作，后端计算，包含全部已选输入。只做变量替换的展示如暂时保留，应标为“模板变量预览”，不能标为最终结果。没有实际镜像时显示“配置预览，镜像待选择”，临时验证占位值不可保存为发布产物。

用户可记住编辑器偏好、目录宽度；不得把上次生产环境自动当作新发布的默认目标。上下文由明确导航和绑定确定。

## 5. 配置来源与编辑规则

### 唯一事实来源

已绑定的基础定义版本 + 目标环境的差异/引用 + 本次明确的产物及系统目标，经过后端唯一渲染链生成部署输入。最终渲染文本不另存为可随意编辑的第二份配置。

公共模板更新后，已有环境保持绑定版本，页面提示可比较/升级；不得因为刷新页面自动采用最新模板。同步某项配置与发布某个镜像是两个独立动作。

字段显示有效值和来源，例如“1Gi · 当前环境设置”“512Mi · 基础定义”。单位输入使用数值与单位选择并规范化，避免输入 `2` 后猜成 2Gi。表单的申请值与上限分开展示。

### 表单与 YAML 如何兼容

1. 表单只处理能够稳定识别的资源与字段。目标按资源类型/名称/容器名识别，多工作负载、多容器时必须选定目标，不能按数组第一个猜测。
2. 一个字段只有一个当前写入来源。表单设置环境覆盖后，YAML 内相应位置显示覆盖提示及跳转；修改基础值不会隐式移除环境覆盖。
3. 第一阶段支持整份 YAML 新增/修改，包含公共定义与当前环境定义两种明确保存范围。整份文本编辑不依赖表单覆盖的字段范围；表单只作为同一草稿的局部编辑辅助，不承诺任意 YAML 无损双向转换。
4. 日常的可识别字段修改可映射到已有环境覆盖。复杂的整份编辑允许生成仅绑定当前环境的不可变定义版本，并保存来源基础版本；其他环境及公共默认版本不变。编辑器保留作者的模板表达式，不把注入实际镜像/秘密后的最终渲染文本用作可写源文件。
5. 当前“创建服务版本”接口会更新服务公共 current_revision_id，不能直接复用为仅当前环境保存。后端必须区分版本作用域及读取可见范围，原子更新所选环境绑定；升级公共定义时显示环境专用版本与来源基础的差异，不自动覆盖。自动生成复杂补丁/三方合并可后续完善，不应成为支持整份编辑的前置障碍。
6. 变量表达式、注释、多文档文件、未知字段应保留；无法保证保留时阻止模式转换并说明具体字段，不默默删减。环境内新增或删除资源要在差异中明确显示。

覆盖字段应区分三种意图：继承、设置具体值、显式移除。旧空字符串继续按继承解释；显式移除是待设计的新语义，需后端验证及迁移兼容。界面用“不设置此字段”，不能承诺“不限额”，因为集群策略仍可能添加默认值或拒绝请求。

### 整份 YAML 新增/修改的交互约定

- 模板只是起始内容。可以从最小 Deployment/Service 模板创建，随后直接粘贴、修改完整 YAML，或添加 ConfigMap、Ingress、PVC 等文件；不要求先在模板库加字段才能编辑。
- 继续保留文件名、多文档 `---` 和单页编辑。右键服务新增文件，点击文件定位对应 `kind:`。整份替换前保留草稿撤销和前后差异，不能悄悄清空其他文件。
- 选择测试环境后，默认保存为“仅测试环境”；公共定义在明确的独立入口修改。编辑某个环境不能顺带更新公共服务版本或其他环境。
- 同一字段若已有变量或资源覆盖，编辑时显示最终值和来源。修改其 YAML 字面值时，必须明确把写入权转移到 YAML 并原子移除冲突覆盖，或转去修改当前覆盖；禁止提示保存成功但实际值仍被另一层覆盖。
- YAML 与表单共享草稿及版本 token。支持的字段双向定位；模板表达式/未知字段不能映射时保持原文，相关表单字段标明由 YAML 管理。切换视图不整份重写原文。
- 完整编辑仍受资源范围、目标环境、权限和实际 Kubernetes API 支持约束。集群级对象、跨 Namespace 资源不因“粘贴整份 YAML”而获得额外部署权限。普通服务发布不承担 CRD 安装等集群管理任务。
- 删除文件或 YAML 文档先形成明确的移除计划，不等于立即删除线上对象。预览列出新增/修改/拟移除资源；只允许处理有明确服务归属的资源。PVC/数据资源默认保留并提示，不按“文件已删除”自动销毁。

### env 日常修改的标准约定

“平台环境变量”用于渲染配置，“容器 env”是提交到工作负载的运行配置。不能因为名字相同就隐式把全部平台变量注入容器；最终 YAML 必须显示实际的注入关系。

少量普通值支持直接编辑 `env`；跨环境经常变化的值可以采用模板变量；多项应用配置可以放 ConfigMap；敏感值使用目标环境的 Secret/加密凭据引用。均保留 Kubernetes 原生 `env`、`envFrom`、`valueFrom` 形式，表单不限制原生写法。

下面是放在选定容器下的模板片段（不是一份可独立部署的完整 YAML），变量需要分别在目标环境配置：

```yaml
env:
  - name: LOG_LEVEL
    value: "{{.LOG_LEVEL}}"
  - name: DB_HOST
    value: "{{.DB_HOST}}"
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: "{{.DB_SECRET_NAME}}"
        key: password
```

例如测试的 LOG_LEVEL=debug、DB_HOST=test-db、DB_SECRET_NAME=risk-test-db；生产独立保存 info、prod-db、risk-prod-db。示例只引用 Secret 名称，不保存密码；实际服务须验证自己的应用配置项和目标 Secret。也可以直接在某环境 YAML 中写 `value: "info"`，不强制所有常量变量化。

env 编辑与预检至少包括：

- 精确定位工作负载及容器；在同一容器内按 env 名称操作，不能因列表排序变更误改别的变量或边车。
- 新增、修改、删除、恢复继承、空字符串含义独立；`value: ""` 是空值，删除 env 项不等于写空值。
- 检查重复变量、`value` 与 `valueFrom` 冲突、缺失模板变量、字符串类型以及 ConfigMap/Secret 引用。存在有序变量引用时保留顺序，不为了排序美观改变语义。
- 表单输入字符串按 YAML 字符串正确序列化，包含冒号、引号、换行、布尔/数字样式的内容不能改变 YAML 类型；模板渲染也必须验证转义后的结果，不以字符串替换安全性作假设。
- 秘密只显示引用和引用是否可用，禁止通过预检、日志或对比打印密码；引用存在性按目标集群和 Namespace 检查。无权限/网络失败显示“未完成检查”，不能默认为存在。
- 编辑变量页后发布预览能明确看到对应容器字段发生变化；变量未被任何资源引用时提示“当前未使用”，不能显示已影响应用。

修改 Deployment Pod 模板中的 env 后，本方案通过一次正常部署更新工作负载；修改被 env 引用的 ConfigMap/Secret 内容则需要另外识别消费关系并生成受控滚动更新计划，不能仅依据 Deployment 原文是否变化判断是否要更新。Kubernetes 官方文档明确 ConfigMap 环境变量不会自动刷新；subPath 文件也不会自动接收 ConfigMap 更新。普通卷投影更新不代表应用已经重新加载配置。

新建 ConfigMap 与修改挂载要在同一次草稿中预览；常规发布按依赖检查并应用，再等待工作负载就绪。预检通过不代表应用业务健康，最终仍需现有探针及用户已配置的验证步骤。

### 配置文件、域名与账号密码

- 服务专属的 Deployment、Service、Ingress、配置文件及挂载在该服务内管理。环境共享中间件地址、共享配置在环境内管理，服务明确引用；不能复制出多个没有来源提示的“相同值”。
- 优先使用已有模板或手动 YAML；表单是编辑辅助，不自动创建用户未选择的 Ingress、PVC、ConfigMap。
- 密码与密钥使用凭据/Secret 引用，编辑器、预览、对比、审计均不展示秘密正文。普通配置文件中的潜在密码也需在实施时纳入脱敏校验，不能仅依赖字段名是 Secret。
- 生产与测试域名、连接地址、凭据、PVC 独立。复制引用时需验证目标作用域及资源存在性，不能认为同名就是同一个资源。
- PVC 解除关联、调整容量、删除、迁移各有不同含义。常规配置保存不得自动删除数据，已有不可变字段保护继续保留。
- Helm 遵循实际 Chart values 与 schema，不能假设所有 Chart 都有 `resources.limits.memory`；宿主机沿用对应模型，只统一交互和状态语义。
- 不在重构中改变现有变量优先级或自动激活此前未参与 YAML 渲染的全局变量。先给出来源清单，后续改语义必须迁移与逐项比较。

## 6. 保存、发布与状态

主操作收敛为“保存配置”和“发布”。可以提供“保存并发布”，但点击后进入一次汇总差异确认，不要多层连续确认。生产沿用既有保护规则，本轮不扩建审批功能。

一次保存原子提交当前服务环境的变量、资源及配套配置。失败必须全部不保存；并发冲突返回明确差异，保留本地草稿。不能用前端连续请求替代后端事务。

保存与发布入队属于两个可独立失败的动作：若已保存但入队失败，明确显示“配置已保存，发布未提交”，允许用同一配置版本重试；不能显示成全部失败或直接成功。重复点击/网络重试使用幂等键防止重复运行。

页面把两类状态分开：

| 配置/发布状态 | 说明 |
| --- | --- |
| 未保存 | 仅本次编辑草稿；离开前保护 |
| 已保存、待发布 | 保存输入与最近成功应用版本不同 |
| 发布中/发布失败 | 显示对应运行、步骤、原因；不能提前标为已生效 |
| 最近成功应用版本 | 有可追溯快照及就绪检查结果；仍要单独显示当前运行健康 |
| 实际状态未知/与期望不同 | 集群读取失败、外部修改或控制器变化；未知不能显示成正常 |

运行健康继续展示 `CrashLoopBackOff`、`ImagePullBackOff` 等实际原因和事件。发布成功与后来运行健康异常可以同时存在。已保存配置、发布快照、当前集群对象分别可查看，并显示观测时间。

## 7. 三条日常操作路径

### A. 测试内存从 1Gi 调整为 2Gi

1. 从服务页或测试环境页打开 risk_server，顶部固定显示测试目标。
2. 常用配置选定容器，将内存上限从 1Gi 改为 2Gi；页面显示当前有效申请值并立即校验。
3. “保存并发布”展示本次差异：只改当前环境内存，保留当前已应用镜像摘要，影响该工作负载。确认后执行同一发布流程。
4. 页面跟踪部署步骤与就绪结果，失败直接展示原因、日志和事件。生产配置不变。

如果没有可追溯的当前固定镜像，不能自动用最新构建冒充当前镜像：改为明确选择制品/首次构建。若发现实际镜像与记录不一致，先提示差异，不能无提示覆盖人工变更。

### B. 将测试验证过的版本发布到生产

1. 从测试环境的成功发布记录或制品记录发起“发布到其他环境”，选择生产。
2. 展示同一不可变镜像、Commit、来源构建以及测试部署记录。构建成功只表示制品生成成功；不能自动标记成业务测试通过。
3. 使用生产已经保存的配置，例如内存 4Gi、生产域名和生产数据库引用；不复制测试资源配置。若生产有尚未发布修改，必须显示将采用的具体配置版本和差异。
4. 执行绑定生产的发布工作流，保留其必要节点与现有门禁，目标不能在执行弹窗临时改写。完成后检查生产运行状态。

不同集群、不同 Namespace 不构成重新构建的理由。若编译期写入环境地址、架构不兼容，或产物无法在目标仓库拉取，则明确提示不能直接复用，不在后台偷偷重构建或复制镜像。

### C. 把某个配置变化同步到另一环境

在环境差异表只选需要的字段，例如健康检查路径或 CPU request，选择目标、预览、保存。来源与目标版本、未选字段和最终影响都清楚可见。

默认不选择生产，不全选字段；凭据/数据库地址/域名/PVC 使用独立目标配置，不随通用同步带走。需要同值时明确映射目标引用。资源的单个字段可以选择同步，不要求整块复制四个 request/limit。

同步保存不自动发布。多个目标保存先按同一快照校验并原子提交；跨多个集群的部署不能承诺原子回滚，应逐目标展示结果。

## 8. 后端实现边界

建议新增统一服务环境配置契约，逐步兼容已有 `/config`、`/assets` 接口：

- 聚合读模型包含：身份/目标版本、基础版本、变量与来源、配套配置、最终值、最近发布及观测时间。实际集群对象按需单独读取，不阻塞配置编辑。
- 服务端统一预览包含草稿变量与 assets，使用部署同一渲染链。响应分别标明本地结构校验、目标集群 dry-run、权限/网络检查的结果；没有做的检查不可显示为通过。
- 保存锁定服务/环境，复核完整 token（包括基础、环境绑定、变量、assets）。聚合版本可先由现有行修订组合得出；可恢复的不可变配置历史是新增能力，不能只用可变行和 UI 序号假装版本历史。
- 统一发布入口提交明确的 intent：构建并发布、已有产物发布、仅配置发布。旧执行框与发布草稿使用同一能力查询、同一请求校验及同一执行链；不另造第三套执行逻辑。
- 仅配置发布以目标环境最近可验证的成功快照中的固定镜像为准，绝不按服务“最新构建”取值。多容器逐一保留各镜像，不能统一替换边车。
- 排队前冻结本次配置和目标；执行前目标已改变、权限失效时拒绝旧任务。同一环境服务的发布串行或冲突拒绝，过期任务不能在新发布之后覆盖回来。
- 凭据只冻结引用，当前代码在执行时再读取；不能因此宣称秘密值不可变。应记录可用的凭据版本/变更标识；发生轮换时提示重新预检或按提供方版本读取，历史回滚不得恢复已撤销秘密。
- 配置文件和秘密更新不一律等于应用已读取。根据注入方式显示是否需要滚动重建；只对需要的工作负载执行受控更新。未来 checksum 注解不得泄露秘密正文或低熵秘密的可猜测散列。
- 回滚从明确历史快照生成新的发布记录；展示将回退镜像与配置的范围，保留目标绑定和数据保护，不把数据库/PVC 数据也描述为可自动回滚。

## 9. 实施顺序与验收

### 阶段一：先让配置看得清、改得少（已交付第一版）

- 补齐 CPU/内存环境对比；将顶部模板预览与完整后端预览区别命名，完整预览合并所有草稿输入。
- 服务、环境两个入口复用工作台；CPU/内存入口前移，保留现有 YAML 文件目录。
- 后端聚合保存原子化，前端统一草稿/离开保护；基础版本、覆盖来源、目标始终可见。
- 实现整份 YAML 新增/修改及仅当前环境版本保存，支持原生 env/envFrom/valueFrom；保存作用域、覆盖冲突与字段来源必须清楚。模板是起点，不限制可编辑字段。
- 不改变现有保存不部署的默认语义；旧接口兼容读取并对齐写入校验。

验收：两种入口修改和读回相同；测试 1Gi/生产 4Gi 比较完整；混合修改变量与资源失败时全部回滚；多容器只改指定容器；并发冲突不覆盖；快速切环境不串响应。测试环境整份 YAML 编辑后，公共版本和生产绑定不变；新增 ConfigMap/修改 env/挂载/探针后完整预览正确；空值、删除、顺序引用、重复 env、特殊字符串、覆盖冲突有明确行为。测试使用独立数据库和隔离资源。2026-10-02 的真实浏览器验收已覆盖上述工作台主流程；结果见 `local/dev/browser-check/environment-workbench-v1.cjs`，实际业务写入为 0。

### 阶段二：日常改配置与上生产都在同一链路完成（已交付配置发布基础能力）

- 统一工作流执行与发布草稿能力，增加保留当前镜像的配置发布；支持从当前环境成功发布记录发起配置发布。跨环境直接晋级仍保留目标环境配置，后续再扩展入口。
- 增加可追溯配置版本、统一汇总差异、幂等提交及清楚的保存/入队部分成功反馈。
- 准确显示发布进度、实际健康、事件和配置文件是否需要重启。
- 串联标准步骤：冻结产物与配置 → 目标及资源预检 → 应用配置资源 → 工作负载更新 → 就绪/已配置验证 → 归档结果。首次无制品时明确走构建；日常 env/资源调整保留当前制品；跨环境上线保留目标自己的配置。界面默认显示简洁步骤，失败展开诊断。

验收：测试构建 A、后来构建 B，但仅配置发布仍使用当前 A；生产复用 A 且保留生产资源/域名/凭据；入队后改配置不影响该运行；重复点击只创建一次；目标变化拒绝；必要节点及已有审批不被跳过；重启恢复、超时失败可见。变更被 env 引用的 ConfigMap 时，消费者更新及实际新 Pod 配置验证通过；缺少必需引用阻止发布，探针失败不标成功，查询敏感 env 不进入验收日志。明确区分镜像回退、配置回退和不可回退的数据变更。

### 阶段三：高级习惯和效率（未开始）

- 在阶段一整份环境 YAML 编辑基础上，完善自动差异提取、按字段同步和公共版本三方合并；不重复建设另一个编辑器。
- 多环境紧凑比较视图；只按需加载被比较环境，不一次请求所有服务全部 YAML。
- Git 管理单独设计来源、写权限、提交/PR、同步状态和冲突处理；平台管理与 Git 管理必须明确互斥写入归属。

验收：未知 CRD、注释和多文件保留；字段不被表单/YAML双重覆盖；继承/设置/移除语义明确；目标资源改名能检测补丁失配；秘密不进入正文或日志。对 Helm/主机只展示实际支持的能力。

每阶段都做真实浏览器点击、切换、保存失败恢复和视觉验收。浏览器受控 API 验证与真实集群部署验证分开记录；完成 UI 验收不能被描述成生产发布已经测试成功。上线前先做已有环境渲染结果一致性比较，不批量重写业务配置或历史快照。

## 10. 官方资料核对与适用范围

2026-10-02 直接读取以下官方文档，取其具体机制作为参考，不把外部平台能力当成 AxiOps 已实现功能：

- GitLab《Deployment safety》：同一目标部署并发控制及过期部署保护。支持本方案对发布串行、版本检查的要求。
  `https://docs.gitlab.com/ci/environments/deployment_safety/`
- Argo CD《Helm》：不同 values/parameters 输入有明确优先级。借鉴“解释最终值来源”，不照搬其字段层级到 AxiOps。
  `https://argo-cd.readthedocs.io/en/stable/user-guide/helm/`
- Kubernetes《ConfigMaps》：环境变量形式的配置更新需要 Pod 重启；普通卷投影最终更新不代表应用会热加载，subPath 挂载不能指望自动更新。支持本方案明确区分保存、应用与运行生效。
  `https://kubernetes.io/docs/concepts/configuration/configmap/`
- Kubernetes《Define Environment Variables for a Container》：区分 env、envFrom 及变量引用顺序；作为直接 YAML/表单编辑的一致语义依据。
  `https://kubernetes.io/docs/tasks/inject-data-application/define-environment-variable-container/`
