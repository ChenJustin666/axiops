# 服务删除、恢复、名称与目录

## 垃圾桶与彻底删除（2026-10-17）

YAML、Helm 服务使用同一生命周期：服务目录更多选项 → 删除服务 → 左侧“垃圾桶” → 恢复或彻底删除。移入垃圾桶后保留编码和原配置；彻底删除必须输入完整服务编码，后端重新检查引用和执行状态。彻底删除后可以用相同编码创建新服务，新服务 ID 独立。

彻底删除清理服务身份、配置版本、环境 YAML 版本、内部 Helm values/配套配置、构建配置、专属变量和服务权限绑定。保留历史构建/工作流执行证据、共享模板、共享环境资源、凭据实体和审计；不调用 Kubernetes/Helm 卸载、不删除 Git 或仓库镜像。历史回滚不再适用于已彻底删除的服务。需要停服时，先通过集群管理完成卸载。

只允许彻底删除垃圾桶中的服务，有环境/工作流引用、未结束任务、资源回收、仍在执行的 Helm 或主机操作时拒绝。删除事务对服务加锁，任何一步失败全部回滚。

新增 `POST /api/v1/services/:id/purge`，body 为 `{"confirm_code":"服务编码"}`，要求服务 delete 权限。deletion-check 增加 can_purge。无需迁移。

## 用户操作

### 保存当前服务配置（2026-10-10）

服务与配置默认打开具体环境，保存只更新当前服务的当前环境。例如 A、B 都从同一模板创建，修改并保存 A 的 YAML 或变量，不修改 B，不回写模板库，也不自动更新其他环境或执行部署。

1. 在服务目录选择 A，再选择要修改的环境，解锁编辑，修改后点击“保存环境配置”。
2. 只改测试环境时，先选择测试环境，修改后点击“保存环境配置”；其他环境保持原样。
3. 需要同步同一服务的环境配置时，点击“对比并同步”，明确选择目标环境、变量或 YAML，检查差异后确认。普通变量和 YAML 默认不勾选；生产目标仍需确认。
4. 需要修改供后续服务创建使用的模板时，进入独立“模板库”保存。已创建服务使用各自的配置副本，需要采用新模板时显式“更换模板”。

保存期间不能切换环境或通过正常目录切换服务；即使页面上下文发生变化，迟到的保存响应也不能刷新或覆盖另一个服务的编辑器。

左侧文件选择按服务独立记录：A 的 `service.yaml` 不会让 B 的同名文件高亮。直接点击 B 的文件会切换到 B 并定位对应 YAML 区域；返回 A 会保留 A 上次选择的文件。跨服务点击仍先检查未保存修改或正在保存的状态。

### 手动创建后改用模板（2026-10-10）

不要删除重建。手动、模板是配置的创建来源，原服务可以保存来自模板的新版本：

1. 如果服务已经删除，先进入“已删除服务”点击“恢复”。恢复保留同一服务身份，不触发构建或部署。
2. 在服务目录中右键服务，或点击该行“⋯”，选择“更换模板”。
3. 选择目标环境及模板库的已保存模板；目标服务自动带入且不能修改。填写模板参数，需要核对正文时展开“查看 / 调整完整 YAML”。
4. 点击“保存当前环境”，校验并确认。页面显示该服务的目标环境配置，构建配置和执行历史保留。
5. 其他环境不跟随修改。需要更新时切换到对应环境编辑，或通过“同步配置”明确选择目标、字段并核对差异，再执行目标环境工作流。

如果从目录顶部“模板”进入新建，并填写了已有服务名称，弹窗会提供“使用已有服务「名称」更换模板”，点击后保留已选择的模板，转为更新原服务，无需关闭后重新选择。没有该服务更新权限时，不提供替换按钮。

Kubernetes YAML 更换模板保存目标环境独立配置，不修改服务名称、编码、代码仓库或镜像绑定，不自动部署。创建来源标签仍描述最初的创建方式。目标或参考配置在选择模板期间被别人更新时，本次保存被拒绝，刷新后重新核对，避免覆盖他人最新修改。Helm 更换模板沿用基础版本创建流程。

服务配置的目录行显示应用图标、展示名称、固定编码和交付类型（YAML / Helm / 主机）。名称和编码过长时省略，悬停查看。行右侧“更多”菜单提供“编辑名称”和“删除服务”；列表上方有“已删除服务”。菜单按服务作用域权限显示。

编辑名称支持 1–64 个字符，可使用中文。创建时仍按既有服务命名规则生成编码；后续名称仅作为展示标签，编码不改变。已有 image_name 保持不变；如果尚未绑定镜像名，重命名时固定原先自动生成的镜像名称，防止之后打开构建配置时随展示名称变化。构建配置默认名称优先使用已绑定镜像叶名称。不会提交构建或修改运行中的资源。

删除确认窗口先读取引用检查。环境版本覆盖、工作流节点 service_id 引用、未完成 build_run、未完成 workflow_run 阻止删除；已经终止流程中未启动的 pending 节点不构成活跃任务，但仍在 running/dispatching/cancelling 的任务会阻止删除。工作流引用无论启停均保留检查，需到工作流编辑移除对应节点。

环境关联可以在确认窗口单独解除，需要服务删除权限及该环境更新权限，并检查关联 revision，拒绝覆盖别人新修改的配置；进行中的任务会阻止解除。此操作只移除 environment_service_override 中的版本、镜像和副本覆盖，不卸载应用，不删除服务变量或历史部署快照。历史部署数量会提示用户集群应用可能仍在运行。

确认删除将服务标记为 `deleted`，正常列表默认排除，可以在垃圾桶恢复到 active。移入垃圾桶时保留 ID、编码、revision、构建配置、日志、环境变量和部署记录；需要复用编码时先彻底删除。`inactive` 是原停用状态，不自动视作删除；恢复只处理 deleted。彻底删除规则见文首。

## 后端与并发

- `GET /api/v1/services/:id/deletion-check`：返回 can_delete、blockers、deployment_history。
- `DELETE /api/v1/services/:id`：服务 delete 权限；事务中重新检查后标记 deleted，不信任页面先前的检查结果。
- `POST /api/v1/services/:id/restore`：服务 delete 权限；恢复同 ID，不创建任务。
- `POST /api/v1/services/:id/rename`：服务 view/update 权限，body 为 name。deleted 服务不能改名。
- `DELETE /api/v1/services/:id/environment-bindings/:environment_id?revision=…`：显式解除环境版本覆盖。
- 通用 Update 不允许修改 deleted 服务或写入 deleted 状态，避免绕过专用删除检查/恢复权限。
- 共享服务行锁用于删除、创建/更新工作流引用、创建工作流执行/回滚、构建提交、服务 revision 和环境关联写入。引用/任务写入同时校验服务 active；删除事务使用 READ COMMITTED，等待写入完成后重新查询引用，避免预检与提交之间的竞态。
- 不需要数据库迁移；已有 VARCHAR status 使用新状态值。原保留记录和原有停用服务没有批量变更。
